## 3. What Worked (已验证的技术决策与关键突破)

1. **Schema 注入范式演进**：
   - 早期对比“列信息 RAG 检索”与“System Prompt 静态注入”，在单表场景下直接用类似 Python 伪代码注入 System Prompt 效果最好（Token 控制在 2400 左右）；
   - 多表扩展后，演进为先通过 `parse_query_v2` 根据 Top-5 字段相关度定位唯一表，再动态组装表 Schema，避免全库字段爆炸。
2. **日期区间幻觉的工程根治**：
   - 发现纯靠 Prompt 无法根治“本月、上周、近30天”跨年或动态日期的幻觉（尤其是知识库固定时间样本会导致 LLM 机械复用历史年份）；
   - **解法**：前置自研日期解析微服务，在用户 Query 进入大模型前直接计算出绝对时间区间（如 `2025-05-01 至 2025-05-31`）显式注入，彻底消除时间推理幻觉。
3. **4+1 并行超时投票机制 (容灾防幻觉)**：
   - 针对大模型在同一复杂 SQL 上重复 5 次偶发 1 次幻觉的顽疾，设计工作流主节点（主力 LLM）驱动，后端异步并发调用 4 个子 LLM；
   - 设置严格的异步超时时间（Timeout），超时未完成直接熔断，只对在规定时间内返回的结果进行多数表决（Majority Vote），既防止长尾延迟，又为大模型幻觉做了强健兜底。
4. **Dify 开源底座深度源码改造**：
   - 深入改写 Dify 前端 Next.js `middleware.ts` 拦截解析企业内部 SSO Token；
   - 改写后端 `passport.py`、`conversation_service.py` 识别用户真实工号与权限组，以 SQL Where 条件（行级/列级/表级）动态注入的方式实现企业级数据权限隔离。
5. **开源模型微调与量化加速**：
   - 基于 Qwen2.5-Coder-14B-Instruct 进行 SFT 微调；
   - 引入 vLLM + 模型量化，通过定制 `<|endoftext|>` 截断与精简 Constraint，将单次 SQL 生成耗时由 12s 压降至 3s。
6. **2.0 混合检索 RAG 重构**：
   - 废弃旧版单纯的“SQL LIKE + Reranker”链路，改用 ES 8.12.2 + IK 行业分词 + 向量检索多路召回；
   - 2025年6月进一步引入 Agent 语义分词块，直接解决生僻长尾药品枚举值的召回遗漏问题。

## 4. What Didn't Work / Traps (踩坑与反直觉教训)

1. **纯单模型微调的局限**：单纯依靠微调小模型（如开源 14B）在复杂 SQL 和少见口径上仍然不如 GPT-4 稳定，且迭代周期长。最终结论是：在工业生产中，**Prompt Engineering + Few-shot 动态样本库 + 多路 RAG + 工程化拦截（预计算/投票）** 的投入产出比（ROI）远高于单一依靠模型微调。
2. **知识库样本写死绝对时间**：早期 Few-shot 样本中的 SQL 时间写死为 `2024-12-10`，导致大模型在 2025 年提问时直接抄袭 2024 年年份。必须将知识库样本全部改写为相对时间参数，并使用 OpenAPI 标准 YAML 格式。
3. **实体切分冲突（如“聚宝盆”）**：用户提问“重庆健君医药有限公司（聚宝盆）入库金额”，大模型误将“聚宝盆”（既是业务模式又是供应商名称后缀）切分为两个查询条件，导致查无数据。Prompt 约束容易“按倒葫芦浮起瓢”，最终改由专门的 ES 实体对齐服务前置归一。
4. **数据解读（DeepResearch 路线）搁浅**：早期曾尝试加入基于 OpenAI DeepResearch 范式的全自动数据异动归因与报告生成功能，但因算力消耗过大、分析结论主观性过强、业务不买账，在 2.0 中被标记为 DEPRECATED。
