## 核心要点与考题精要

本文记录了腾讯微信事业群（WXG）针对 Coding Agent 岗位的一面硬核考核。面试呈现高压与多维覆盖特征，涵盖现场白板手撕、C++ 底层并发、Coding Agent 核心记忆与架构选型、生产级容器迁移与上下文恢复、长任务 Goal 防漂移，以及模型能力边界下的工程补偿策略。

### 1. 手撕代码：大数乘法与“脏题”应对逻辑（Q2）
- **大数乘法核心算法逻辑**：
  - 输入为两个以字符串形式表达的非负超大整数（长度可达数千位），直接转数字会导致整型溢出。
  - **核心解法**：基于竖式乘法原理。长度为 $M$ 和 $N$ 的两数相乘，结果最大长度不超过 $M + N$。
  - **关键步骤**：
    1. 预分配长度为 $M + N$ 的整型数组 `result` 初始化为 0；
    2. 双重循环逆序遍历两字符串：`num1[i]` 与 `num2[j]` 相乘，所得乘积累加到索引 `i + j + 1` 处；
    3. 进位处理：从后往前遍历 `result` 数组，将当前位大于等于 10 的部分进位累加到 `i + j`，当前位取模；
    4. 去除前导零并拼接成最终字符串输出（若结果全为 0 则返回 `"0"`）。
- **“脏题”与无边界题目考核的本质**：
  - 题目没有给出现成测试用例、边界说明与标准输入格式。
  - 考核重点不在于死记模板，而在于面对未充分说明的“脏需求”时，能否自主在白板上完成“接口定义、边界判断、符号与前导零处理、模块分拆与鲁棒性实现”。

### 2. C++ 底层与并发编程：原子计数与无锁机制（Q3）
- **C++ 原子计数原理**：
  - 在多线程高并发计数（如请求统计、引用计数）场景下，传统互斥锁（`std::mutex`）由于涉及上下文切换与内核态竞争，开销极大。
  - C++11 引入 `std::atomic<int>`，底层依托 CPU 硬件级原子指令（如 x86 的 `LOCK XADD` 或 `CMPXCHG`，ARM 的 `LDREX/STREX`），通过 CAS（Compare-And-Swap）机制保证单指令原子性。
- **内存序（Memory Order）权衡**：
  - 针对单纯自增计数（如访问量统计），可选用宽松内存序 `std::memory_order_relaxed`，免除内存屏障（Memory Barrier）开销，性能最高；
  - 针对涉及多线程依赖可见性或事件发布的同步场景，需采用 Acquire-Release（`memory_order_acquire` / `memory_order_release`）或严格顺序一致性（`memory_order_seq_cst`）。

### 3. Coding Agent 核心架构与设计选型（Q4, Q5, Q9）
- **Coding Agent 的记忆体系设计**：
  - **分层记忆治理**：
    - *短期工作区记忆（Scratchpad）*：当前正在编辑的代码片段、终端最新输出与测试运行报错；
    - *会话记忆（Conversation Memory）*：多轮交互历史，通过滑动窗口与结构化分槽摘要控制 Token；
    - *项目知识记忆（Repo Memory）*：基于 AST 语法树结构化解析生成的符号索引库（Functions/Classes/Call Graph），结合向量与全文检索按需召回相关依赖文件。
- **架构对比：自研 Agent vs Claude Code vs Codex**：
  - *Codex*：早期单步补全与单文件端到端代码生成模型，缺乏自主环境交互与纠错循环能力；
  - *Claude Code*：以 Subagent 隔离、文档驱动规范（Spec-Driven）、Smart Zone 上下文有效区为核心的企业级原生 Agent，强调沙箱运行与闭环自动化；
  - *自研 Agent 定位*：需回答清楚结合自身业务场景（如垂直领域 SDK、特定规范代码库、内部测试基建）所做的差异化定制。
- **模型选型权衡**：
  - Coding Agent 优先选择在代码推理、工具调用（Function Calling）与长上下文召回表现优异的基座模型（如 Claude 3.5 Sonnet、DeepSeek-Coder、Qwen2.5-Coder）；针对本地与高频补全场景结合轻量级模型分层分流。

### 4. 生产级工程落地：评测、容器迁移与目标防漂移（Q6, Q7, Q8）
- **Coding Agent 的评测体系设计**：
  - 不能仅靠肉眼评测，必须构建自动化评测流水线：
    - ① **离线基准（Benchmark）**：引入 SWE-bench / HumanEval 等经典评测集，计算 Pass@1 / Pass@k 指标；
    - ② **语法与静态分析率**：生成的代码是否能 100% 通过 AST 解析与 Linter 检查；
    - ③ **单元测试闭环执行率**：Agent 自动生成测试用例并执行，统计单测通过率与代码覆盖率增量；
    - ④ **线上真实任务抽样**：抽取实际开发者 PR 采纳率、人工介入修改字符数比例。
- **云端容器迁移与上下文状态恢复**：
  - 云端执行 Coding Agent 时，执行环境常运行在 K8s 容器或沙箱中。若容器发生扩缩容、故障重启或跨宿主机热迁移，必须避免上下文中断丢失。
  - **解耦落地架构**：
    - 状态不保存在容器内存中，而是在每步 Agent Loop 执行完毕后，向外部分布式存储（Redis / 对象存储）提交包含完整“对话历史 + 局部环境变量 + 执行游标 + Git 工作区未提交 Diff”的 Checkpoint 快照；
    - 新容器唤醒时，根据 Session ID 拉取快照，拉取 Git 临时分支，重建 AST 索引并无缝恢复执行循环。
- **长任务中 Goal 持续推进与防行为漂移**：
  - **行为漂移根因**：随着循环轮次增加，工具返回的海量日志不断稀释初始目标，模型陷入探索子问题的死循环。
  - **工程防御**：
    - *Goal 目标强锚定*：在 System Prompt 顶部和每轮 Loop 输入末尾强制注入原始用户 Goal 核心约束；
    - *任务树动态拆解*：将大 Goal 拆分为明确的子步骤 TODO List，每步工具调用后显式更新步骤完成状态，不允许 Agent 自行跳脱范围；
    - *动态反思与自纠偏*：引入 Critic 机制，在连续多步无实质代码进展或报错反复出现时触发中断与重规划。

### 5. 模型强弱与工程补偿策略（Q10, Q11）
- **模型能力足够强的前提下，Agent 最重要的是什么**：
  - 模型解决的是“单步推理与逻辑生成”，但 Agent 系统的成败取决于**“外部环境工程（Harness）与闭环反馈”**：
    - 工具契约的定义质量与健壮性；
    - 执行沙箱的安全隔离与高可用；
    - 结构化状态机与确定性约束；
    - 优质的环境观察反馈（编译器报错、Linter 提示、运行日志过滤）。
- **模型能力不够的时候，工程上怎么补偿**：
  - ① **架构模式升级**：从放任自由的纯 ReAct 降级为严密的 Plan-and-Execute 混合架构；
  - ② **确定性规则前置拦截**：在生成代码前通过模板和规则注入强约束，后置通过 AST 静态分析和编译器错误拦截；
  - ③ **单测闭环自愈**：利用错误反馈自动构建“代码生成 -> 运行单测 -> 报错回传 -> 自主修复”的收敛闭环；
  - ④ **多候选重排（Best-of-N）**：通过候选生成结合语法与执行验证器做打分过滤。

## 关键引文与面试复盘反思

### 关键引文
> “我现在的判断可能有点反直觉：AI 把业务代码写得越顺，手撕反而越重要。因为能被 AI 顺顺当当写掉的那部分，正好是‘有明确输入输出’的部分。剩下没被写掉的，全是‘没人告诉你输入长什么样’的部分。面试官拿一道脏题出来，就是在看你会不会在没有规格说明的地方开工。”

> “技术债是要还的，尤其是简历上借的那种。简历上借了别人的产出撑门面，被问两句就露馅，这个不怪面试官。”

### 核心复盘与求职战术反思
1. **警惕“干净输入”的刷题惯性**：刷题训练出来的往往是对现成模板和清晰约束的条件反射，而真实面试和生产工程往往充斥着无边界、无输入定义的“脏场景”。必须刻意练习从零定义数据结构、推导边界条件与处理脏输入的能力。
2. **简历借用产物是面试死刑线**：为了充实简历借用组内同事或团队其他成员的产出（如评测体系、容器高可用治理），一旦遇到懂行面试官深入追问细节（指标定义、迁移恢复链路），立刻漏洞百出。“能被扒的简历才是好简历，写得厚但一扒就穿那是给自己埋雷”。
