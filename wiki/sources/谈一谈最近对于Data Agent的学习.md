# 来源摘要：谈一谈最近对于Data Agent的学习

## 来源信息

- **标题**：谈一谈最近对于Data Agent的学习
- **作者**：一包惆怅的辣条
- **发布日期**：2026-10-08
- **原文链接**：https://mp.weixin.qq.com/s/ZLVschLsjfU4u7aNizF8hQ
- **核心议题**：从 0 到 1 构建企业级 Data Agent 时，在范围定界、语义层、SQL 生成模式、工具设计、硬规则校验与评测上的八大系统架构权衡取舍。

## 核心要点

1. **1.0 版本的范围取舍纪律**：做 Data Agent 时，写清“系统不做什么”和写清“要做什么”同等关键。初期应主动排除复杂的财务多表结算、供应链明细与大屏联动，聚焦高频经营分析闭环（销量、客户、预算、同比），复用 BI 已有指标、权限与预聚合缓存。
2. **业务语义层作为版本化软件资产**：
   - 口径不能依赖临时的提示词拼凑，必须作为长期可维护资产（术语、业务对象与关系、指标、任务剧本）；
   - 纳入 Git 版本控制与 CI 自动检查（Schema 合法性、引用一致性、指标安全、权限兼容、行为回归），具备明确 Owner 与回滚机制；
   - 设立受隔离的探索链路支持新指标冷启动，人工审核确认后再固化进正式语义层。
3. **拒绝端到端直写 SQL，引入受约束语义中间态**：
   - 直写 SQL 迫使模型在一次生成中同时猜测业务含义、物理表、字段名、JOIN 方式、过滤条件与聚合方式，错误概率层层放大；
   - 优秀架构采用自然语言 → 受约束业务语义表达（中间态）→ 确定性引擎编译为物理 SQL 或 BI API 的分阶段模式。
4. **工具极简与职责正交**：出口高度收敛（如单一取数出口），避免功能重叠引发模型选择漂移；查询异常需返回具备明确含义的结构化错误码（如累计误用 SUM、超时、越权），驱动模型执行合理分支逻辑。
5. **两道防线：提示词引导与确定性引擎硬校验**：提示词约束模型理解倾向，而业务铁律（累计字段禁用 SUM、同比时间范围、行数限制、只读拦截）必须由后端查询引擎与执行器执行确定性硬校验；引入指纹绑定的短时令牌防范流程绕过。
6. **拒答是合法生产终态**：建立规范的拒答话术库，对域外、越权、字段缺失与超限查询果断拒答，明确告知“为什么答不了”和“下一步该做什么”，严禁硬凑虚假数字。
7. **全链路可归因评测与门禁**：评测覆盖单点单测、口径一致性校验与黄金集回归，核心价值在于精准归因错误发生的系统层级（模型理解、语义定义、权限配置还是工具调度）。

## 关键引文

> "把系统不做什么写清楚，和把要做什么写清楚一样重要。把‘当前版本暂时做不了’只当成系统的能力不足，如今看它更像是 1.0 必要的一部分。"
> "现在优秀的实操项目没有一个是让模型从自然语言直接跳到 SQL……中间表达把这几件事拆开了，模型只管把自然语言变成受约束的业务表达，物理表名、JOIN 方式这些留给后面的确定性模块。"
> "提示词能约束模型的倾向，真正需要兜住的规则得放到查询引擎、翻译器或执行器里做硬校验。"
> "一句话，拒答不算失败……用户拿着一个错数字做了决策，代价比拿不到数字大得多。"
> "先把业务上什么叫对写进语义资产，再把什么情况下允许执行写进确定性引擎，最后才是让模型在这套边界里把理解、路由和组织回答做得更好。"
