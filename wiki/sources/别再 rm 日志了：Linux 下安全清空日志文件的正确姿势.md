# 别再 rm 日志了：Linux 下安全清空日志文件的正确姿势

## 来源信息
- **标题**：别再 rm 日志了：Linux 下安全清空日志文件的正确姿势
- **作者**：AlfredZhao（赵靖宇）
- **发布日期**：2026-10-05
- **原文链接**：https://www.cnblogs.com/jyzhao/p/23200588

## 核心要点
1. **`rm` + `touch` 的高危机理与双重陷阱**：
   - 常驻后台服务（如 FastAPI、Nginx、MySQL）在启动时即已打开日志文件，在内存中持有该文件的 inode 及其文件描述符（FD）；
   - 执行 `rm *.log` 仅删除了目录项中文件名与 inode 之间的映射关系（硬链接计数减 1）。由于进程依旧持有 FD，操作系统判定文件仍在使用中，**不会释放磁盘空间**，磁盘占用依旧居高不下；
   - 紧接着执行 `touch *.log` 会分配全新 inode 创建同名新文件。然而后台进程依然持续向旧 FD 对应的旧 inode 写入数据，新创建的 `.log` 文件永远收不到任何日志，导致**磁盘空间锁死且新日志静默丢失**，直到服务彻底重启。
2. **单文件原地安全截断：`true > 1.log`**：
   - 清空单个日志文件推荐使用 `true > 1.log`（底层由 Shell 直接调用系统调用 `open(..., O_TRUNC)`）；
   - 在保持文件原有 inode、访问权限和后台进程打开的 FD 映射完全不变的前提下，瞬间将文件内容截断为 0 字节，磁盘空间立即由内核回收；
   - 相比单纯的 `> 1.log`，前置 `true` 语义更明确，可避免部分交互式 Shell 环境下对空重定向产生的语法歧义；
   - 注意事项：若 Shell 启用了 `noclobber` 特性，重定向因目标文件已存在而报错，此时需使用 `>| 1.log` 强制覆盖或先关闭该选项；且重定向属于 Shell 语法，无法直接配合通配符批量截断多个文件。
3. **多文件批量安全截断：`truncate -s 0 *.log`**：
   - 清空多个日志文件的首选方式为 `truncate -s 0 *.log`（`-s 0` 即 `--size 0`，指定将目标文件大小重置为 0 字节）；
   - 原生支持文件名数组与 Shell 通配符展开，能一次性对匹配模式的所有文件执行原地截断；
   - 同样保留原文件的 inode、权限和所有者，后台写入进程无需重启即可释放磁盘；
   - 生产红线：执行前务必仔细核对通配符展开范围，严禁误清空非日志文件或数据库核心事务重做日志（如 Oracle `redo.log`）。
4. **三种日志清空方式横向对比**：

| 操作方式 | 适用场景 | 批量支持 | 安全性 / 进程影响 |
| --- | --- | --- | --- |
| `rm *.log` + `touch *.log` | **严禁使用** | - | **高危**：磁盘空间锁死不释放，新日志静默丢失 |
| `true > 1.log` | 清空单个日志文件 | 否 | **安全**：瞬间原地截断，inode 与 FD 不变，进程无感 |
| `truncate -s 0 *.log` | 批量清空日志文件 | 是 | **最推荐**：语义清晰，原生支持通配符批量原地截断 |
