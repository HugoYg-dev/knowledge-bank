# 读代码前先跑的五个 Git 命令

## 核心要点

- 过去一年的文件触达次数可作为变更热点线索，但应在 `src/`、`app/` 等业务目录运行并排除锁文件、变更日志和生成文件；高频变更只有结合文件职责和缺陷聚类才意味着风险。
- `git shortlog` 可比较全历史与最近六个月的贡献者，观察核心维护者是否仍活跃和公交因子；Git 2.47 下文章实测需显式加入 `HEAD` 才有输出，Squash Merge 还会把贡献偏向合并者。
- 按提交信息中的 `fix|bug|broken` 聚合文件能形成粗略缺陷分布图，但结果依赖提交信息质量，也会把文件名或文章标题中的关键词误判为修复记录。
- 按月统计提交数量用于观察项目节奏的形状，长期下降、突然减半或周期性峰谷可能提示人员变化、失速或批量发布，但必须结合项目事件解释，不能把提交量直接等同于健康度。
- 检索 `revert|hotfix|emergency|rollback` 可估计救火频率；高频命中可能反映测试或发布流程问题，零命中也可能只是提交信息不规范，因此同样需要人工核实。
- 这五组命令是两三分钟内建立阅读方向的侦察工具，不是自动诊断报告；最有价值的做法是交叉观察变更热点与缺陷聚集，并结合目录语义、工作流和团队背景解释结果。
