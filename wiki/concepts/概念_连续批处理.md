# 概念：连续批处理（Continuous Batching）

## 定义

连续批处理是提高 LLM 推理吞吐量（GPU 利用率）的核心动态批处理范式。在自回归生成中，每个请求需要的推理步数仅在生成终止符（Stop Token）时可知，传统静态批处理会导致短请求完成后在批次内空等最长请求，造成显存带宽严重闲置。连续批处理通过**迭代级调度（Iteration-level Scheduling）**，在每次前向传播迭代边界动态重构批次成员。

## 核心调度机理

### 1. 选择性批处理（Selective Batching）
- **异构张量扁平化**：当 Prefill 请求（如 4096 Tokens）与 Decode 请求（如 1 Token）混合在同一步时，系统将所有 Token 展平成一维张量 `(total_tokens, hidden_size)`；
- **计算解耦**：无依赖的 LayerNorm、QKV 线性投影与 FFN 模块在扁平流上单次高效批量运行；在自注意力边界处将张量拆分，各请求对其各自长度不同的 KV Cache 执行注意力运算后，再合并回扁平流进入后续模块。

### 2. vLLM V1 调度器四步算法
1. **确定 Token 预算**：以 `max_num_batched_tokens` 设定每步 Token 总上限，`max_num_seqs` 设定并发序列上限；
2. **运行中请求优先分配**：Prefill 请求申请其剩余 Prompt Token 数，Decode 请求申请 1 个 Token，代码层面统一计算 `target - computed`；
3. **分配并锁定 KV Cache 块**：在做出调度决策时就地预留显存块；
4. **剩余预算让渡给等待队列**：未启动的等待请求仅分发剩余 Token 预算。

### 3. 抢占机制与重算成本（Preemption Recompute）
- 显存不足分配失败时，调度器强制释放运行中请求的 KV 块，将其标记为 Preempted 并将已计算 Token 计数置零重回等待队列头部；
- Prometheus 指标 `total_cumulative_preemption_cnt` 是排查长尾延迟（p99）异常飙升的第一核心指标。

### 4. Roofline 视角的算力强度跃迁（Work per Byte Scaling）
- 自回归解码单序列运行时，算力强度仅为 ~1 op/byte，比硬件平衡线低约 300 倍，处于极端内存带宽受限区；
- 连续批处理的核心硬件价值在于**提高单次访存的算力收益（Increase Work per Fetch）**：将单次加载权重的代价在 $B$ 个并发请求间均摊复用，使算力强度随并发量线性提升；
- 在 16-bit 精度下，系统需维持约 300 个并发序列方可跨过硬件平衡门槛进入计算受限区（Compute-bound），这也是推理服务引擎全力维持满批次运行的根本动力。
