# 概念：AI-Native Infra

## 定义

AI-Native Infra 是从零开始、专为 AI 的工作方式设计的基础设施"操作台"和"工具箱"，不是把人类工具"翻译"给 AI 用，而是去掉整个"人类兜底层"。在这个范式中 AI 不再是工具的使用者，而是系统的主导者和决策者。

## 问题背景：隐性人类假设

现有后端系统（Firebase、Supabase、Vercel、AWS 等）都隐含默认前提：使用者是人类工程师且始终在线兜底。体现在三个层面：
- **界面交互层**：需人手动点击/确认/读图表
- **认知负担层**：需人记操作顺序、理解隐含业务逻辑、跨系统建心理模型
- **异常处理层**：报错是"人话"（如 `permission denied`、"请检查配置"）而非机器可操作指令

GUI、CLI、文档本质上都是"人类语义翻译器"，假设背后有聪明人能理解上下文、填补空白、处理异常。

## 应具备的特征

- **状态透明化**：所有系统状态通过标准化 API 暴露
- **接口标准化**：每个操作有明确 API 定义，输入输出格式固定
- **模块可组合**：服务像乐高积木自由组合
- **操作可回滚**：任何变更可程序化撤销/重做
- **逻辑自包含**：不依赖外部"常识"，所有规则明确编码
- **结构化错误响应**：含 error_code、missing_role、fix_endpoint、fix_payload 等可操作信息

## 通用 Infra 与 AI / Agent Infra 的同源与分野

大模型基础设施并非与传统软件工程割裂的独立体系，而是传统 Infra 版图的自然扩张与范式升级：

### 1. 传统 Infra 是 AI 系统的物理底座
高可用、高性能的大语言模型 API 与推理平台，底层依然建立在微服务治理、分布式通信（RPC）、海量数据存储、全链路可观测、容量规划、发布调度与 CI/CD 体系之上。缺乏扎实通用工程底座的推理引擎只能停留在实验 Demo 阶段。

### 2. 资源模型迥异，但核心系统设计思想高度同源
虽然 GPU 带来从 CPU 逻辑事务到高吞吐浮点与显存带宽绑定的物理转变，但其底层工程思想大量继承自经典操作系统与分布式系统：
- **分页内存管理**：PagedAttention 将显存切分为固定 Page 并通过 Block Table 映射离散物理块，本质是操作系统虚拟内存分页机制向 GPU 显存管理的直接迁移；
- **分布式计算分摊**：张量并行（TP）与上下文并行（CP）继承了传统分布式系统将单机超载计算拆分并在集群节点间平衡负载的设计哲学；
- **并发调度机制**：GPU CUDA Stream 异步多流计算，与 CPU 多线程并发/异步 I/O 解决阻塞的思想如出一辙；
- **分布式状态管理**：分布式 KV Cache 的分片、生命周期管理与换入换出，直接借鉴了分布式缓存与分布式存储系统的高可用方案。

### 3. 服务范式跃迁：小卖部模式 vs 旅馆模式

随着 AI 系统从单次推理演进到复杂智能体（Agent），后台服务范式发生了结构性跃迁：

| 维度 | 传统后台与单次推理 API（小卖部模式） | Agent 服务基础设施（旅馆模式） |
| :--- | :--- | :--- |
| **会话生命周期** | 短请求、即调即走、几百毫秒到数秒内完成 | 长耗时、持续驻留、多轮交互、生命周期跨越数十分钟至数小时 |
| **服务状态特征** | **无状态 (Stateless)**<br>请求结束后连接与计算资源即刻释放，状态下沉到数据库 | **强有状态 (Stateful)**<br>会话持续保持活跃，动态维护长短记忆、变量环境与推理上下文 |
| **外部系统交互** | 极少或仅依赖确定的外部 RPC 依赖 | 频繁动态进行外部工具调用（Tool Calling）、代码沙箱执行、网络检索与人机交互 |
| **核心基础设施挑战** | 吞吐量优化（QPS）、水平横向扩容、短时锁与排队 | 长会话生命周期调度、会话状态持久化与快照、记忆分层存储、代码安全沙箱隔离、Agent 行为轨迹可观测与中间评估 |
