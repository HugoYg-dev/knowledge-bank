# 循环工程 (Loop Engineering)

## 定义与定位
在智能体系统设计中，**循环工程（Loop Engineering）**处于智能体架构的最外层控制面。它包裹着底层 Prompt 工程、Context（上下文）工程以及运行工具、追踪状态与错误恢复的 [[wiki/concepts/概念_Harness_Engineering.md|Harness Engineering]]。
循环工程的核心职责在于决定智能体“在每一轮大循环中应该专注于什么任务”以及“在何种条件下应当安全退出循环”，是控制智能体自主性与规避其失控的核心保障。

---

## 四大核心痛点与对策

### 1. Done 终局判定偏误 (Completion Bias)
- **痛点**：传统智能体循环通常依赖模型自身不返回 Tool Call 作为退出信号（即模型自我宣称 Done）。然而，模型的自我判断极不可靠。例如，编码智能体在修改代码后，会自信地给出总结而不调用测试工具，直接退出循环，此时测试可能并未通过或根本没有执行。
- **对策**：引入不被模型控制的外部强约束和校验条件：
  - **最大迭代次数（Max Iterations）**：设定硬性上限，防止陷入死循环产生天量账单。
  - **预算与时限（Budget & Time Limits）**：对 token 消耗、资金花费以及墙上时间（Wall-clock time）进行上限封顶。
  - **无进展检测（No-progress Detection）**：捕捉智能体以相同的参数反复调用同一工具的“鬼打墙”行为。
  - **客观终局校验（Completion Check / Verifier）**：将判定权交由客观的外部信号（例如“测试用例全部通过”、“文件已被成功创建”），或使用一个独立的模型进行客观审查。

### 2. 上下文腐烂 (Context Rot) 与末日死循环 (Doom Loop)
- **痛点**：随着智能体循环的不断迭代，上下文中堆积了大量历史 Tool Call 结果、废弃的思考路径与杂乱的报错信息。上下文窗口膨胀导致模型推理质量下降，即**上下文腐烂（Context Rot）**。而腐烂的上下文会诱导模型做出更愚蠢的决策，生成更多冗余内容，最终加速上下文恶化，形成不断向下的恶性螺旋——**末日死循环（Doom Loop）**。
- **对策**：将上下文视为“预算”而非“无底桶”，采取以下治理手段：
  - **压缩（Compaction）**：当上下文达到一定长度时，对其进行归纳摘要，抛弃细节，只保留高价值的关键脉络。
  - **转存（Offloading）**：将巨大的工具输出（如大段日志、爬取的 HTML）转存至外部文件，仅在上下文中保留指向该文件的引用或简短切片。
  - **子智能体分流（Sub-agents）**：将复杂的子任务委派给独立的子智能体，子智能体执行完毕后只向主上下文返回干净的最终结果，隔离中间过程的噪音。

### 3. 循环场景下的工具设计特殊性
- **痛点**：在单次调用中能良好工作的工具，在循环中可能会因为反复调用、错误传参等引发灾难。
- **对策**：
  - **少即是多（Keep it Simple & Focused）**：避免向智能体提供上百个功能重叠的工具。工具越精简、边界越清晰，智能体选择工具的准确率越高。
  - **写操作幂等性（Idempotent Writes）**：智能体在循环中经常重试。因此，创建、修改等写操作工具必须设计为可安全重复执行（例如，“若已存在则直接返回”，而非重复创建导致脏数据或双重计费）。
  - **自诊断引导式报错（Actionable Errors）**：工具报错时不仅要说明“什么错了”，更要给出“怎么修复”的行动指引（例如，“文件不存在，请使用 find_by_name 工具定位”），因为这些报错会被作为下一轮循环的输入，引导模型自我纠错。

### 4. 执行与校验解耦 (Maker-Checker Separator)
- **痛点**：生成内容的模型（Maker）在自我审计时通常会有盲区，习惯于“自我肯定”。
- **对策**：
  - **Maker-Checker 分离**：执行任务的模型（Maker）与评估结果的信号（Checker）必须解耦。Checker 可以是确定性的逻辑（如编译器、单元测试、Linter），也可以是另一个扮演“批评者”的独立模型。
  - **设定指标，放手自转**：正如 Andre Karpathy 在其 AutoResearch 项目中实践的理念：“不要告诉智能体一步步做什么，而是给它设定明确的成功指标（Success Criteria），然后观察它如何迭代。”系统通过外界 Checker 的真实反馈不断尝试新方案、抛弃失败路径，实现闭环自转。

## 智能体循环的四种类型 (The Four Types of Agent Loops)

智能体系统的运作实际上是在四种不同循环结构中进行选择，每种类型适应不同的任务性质。它们在触发机制、判定终局的主体以及容灾和规模能力上存在显著差异：

- **① 单步交互式 (Turn-based)**：
  - **机制**：由用户输入 Prompt 触发。智能体在单次交互中收集上下文、执行并自我校验，随后将控制权交还给人类。由人类评估输出并撰写下一步 Prompt。
  - **适用场景**：探索性任务，即需求尚在演化、且每一步的输出会直接改变后续目标的场景。
  - **容灾与规模**：高度依赖人工，无法实现规模化运行，但由于有人类实时把关，具有最强的干预和即时纠错能力。
- **② 目标驱动式 (Goal-based)**：
  - **机制**：由包含成功指标与预算的 `/goal` 指令触发（例如“重构代码直至 Lighthouse 评分达 90 分，最多重试 5 次”）。系统使用外部的评估模型（Evaluator）校验目标是否达成，未达成则退回重做。
  - **适用场景**：结果可测量的任务。执行路径不需要人工干预，但需要客观的终局校验。
  - **容灾与规模**：由系统判定 Done 并重试，脱离了人工实时干预，可在一定预算内进行并发尝试。若评估器设计不当，有陷入死循环并消耗天量 token 预算的风险，需通过硬性预算限制进行容灾。
- **③ 时间触发式 (Time-based)**：
  - **机制**：由时钟定时器触发。智能体在固定间隔运行预定义任务（如“每小时检查 PR，修复 CI 报错”），由系统监控执行。
  - **适用场景**：已知的周期性重复工作，仅触发时间呈规律重复。
  - **容灾与规模**：支持通过 `/loop` 在本地持续运行，或通过 `/schedule` 部署至云端，实现常驻后台。通常执行确定性较高的周期性任务，容灾依赖底层运行容器的健康状况和超时自愈。
- **④ 事件主动式 (Proactive)**：
  - **机制**：由系统事件（如 Webhook、消息队列）或调度触发，全自动分流且完全无人在场（No human present）。系统会在运行时动态组装和分派多智能体工作流（如 triage 分流、fix 修复、reviewer 评估）。
  - **适用场景**：长期常驻值守的职责，且无法预测具体事件何时到来，只能在事件到来时自主应对。
  - **容灾与规模**：具有最高的自主性与规模化潜力，多智能体对抗评估提供了自适应校验。由于完全脱离人类监控，必须具备极强的异常捕获与沙箱隔离等 Harness 级容灾机制。

### 循环结构对比

| 循环类型 | 启动触发主体 | 终局判定主体 | 适用任务性质 | 自主程度 | 规模化能力 | 主要容灾机制 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **单步交互 (Turn-based)** | 人类 (Prompt) | 人类 (校验) | 探索性任务 | 最低 (Step-by-step) | 极低 (单线程人工) | 人类介入与即时纠正 |
| **目标驱动 (Goal-based)** | 人类 (Goal/预算) | 系统 (Evaluator) | 可测任务 | 中等 (端到端尝试) | 中等 (支持自动重试) | 限制硬性预算与迭代上限 |
| **时间触发 (Time-based)** | 系统 (Timer) | 系统 (Scheduler) | 周期重复任务 | 中高 (定时自转) | 中等 (后台守护进程) | 云端托管与超时强制杀死 |
| **事件主动 (Proactive)** | 系统 (Event) | 系统 (Multi-agent) | 常驻值守任务 | 最高 (全自动流转) | 极高 (并发多智能体) | 强隔离沙箱与红蓝对抗评审 |

## 从 AI Manager 到 Senior Manager：管理动作系统化

Loop Engineering 的核心演进不仅是调度机制的自动化，更是**管理思想的升维**：

1. **一阶管理（AI Manager）与人肉管理环瓶颈**：
   - 传统使用 AI 时，人类将模型视作会失忆的实习生，需手动提供自包含上下文、清晰问题边界与可客观检验的终点。[[entities/实体_Anthropic|Anthropic]] 对约 40 万条 [[entities/实体_Claude_Code|Claude Code]] 会话的研究证实“表现得像管理者的人更容易成功”；
   - 但此阶段人类依然深陷在“拆任务、看日志、指引下一步”的**人肉管理环（Human-in-the-Loop）**中，系统的总体吞吐量被人类精力严格锁定。
2. **二阶管理（Senior Manager）将管理动作写进系统**：
   - 现代 Coding Agent 的基础自写、自跑、自修（如 Elastic 在 CI 中运行 self-healing loop 月修 24 个 broken PR）在工程上已成立；瓶颈转向跨长任务的高阶决策；
   - Senior Manager 不追求让人把某个 Bug 修得更快，而是将委派、评估、可观测与辅导（Coaching）等二阶管理动作转化为系统内生组件，交付一个**能持续自我修复与演化的系统**：

| Senior Manager 路线 | Loop Engineering 对应组件 | 系统价值与设计目标 |
| :--- | :--- | :--- |
| **将成功经验写成 SOP / Playbook** | **Skills 与知识资产 (`SKILL.md`)** | 让下一轮 Agent 免于重新摸索，将单次人类 Coaching 固化为长期可调用的资产 |
| **建立可复现的 Evaluation Harness** | **Verifier 与自动化评估器** | 制定样例集、指标刻度与 Baseline，避免依赖人类临场感觉，提供确定性尺子 |
| **构建 Tracking UI 记录微观 Trace** | **State 与微观可观测性 (Observability)** | 分数仅说明“好不好”，Rationale 与 Trace 才能解释“为什么不好”并定位模型卡点 |
| **从单兵 Fixer 升维为 Coach** | **Maker / Checker 分立审计回路** | 物理拆分解题者与审题者，消除生成模型自我打分过于宽容的盲区 |
| **真实使用生成新测试样例** | **Memory 与 Data Flywheel** | 静态测试集终会失效，通过真实交互回流驱动系统长期自我强化 |

3. **关键工程落地载体**：
   - **时间调度（Time-pacing）**：利用 cron 调度器（如 `/loop` 指令）周期性唤醒执行，或结合 `/goal` 指令由独立 Verifier 裁决是否达成收敛并安全退出；
   - **分支隔离（Worktree Isolation）**：利用 Git worktree 为并发子 Agent 提供完全隔离的文件沙箱，避免相互踩踏；
   - **外部连接（MCP Integration）**：通过 MCP 协议挂载 CI/CD、代码仓、Issue 追踪等物理工具链；
   - **状态外部化（Externalized State）**：将任务状态落盘为物理文件或进度看板，解决跨 Context Window 重置导致的状态丢失。

## 决定循环质量的两大硬杠杆

构建一条循环流水线门槛较低，但决定循环能否真正**自收敛而非发散失效**的核心在于以下两个硬杠杆：

### 1. 评估的艺术：为什么 TDD 不是 AI 时代的答案
- **传统 TDD 的隐含前提出错**：人类遵守 TDD 依赖内在的求真责任心（对线上宕机、夜间告警与 Code Review 的顾忌）；而 AI 没有隐性维护负担，当测试通过成为其唯一目标时，**古德哈特定律（Goodhart’s Law）**立即生效——为跑通测试，模型会倾向于直接硬编码 `return True`。
- **过度 Mock/Stub 锁死路径确定性**：为防范作弊而编写海量细碎的 Mock 和 Stub，等同于强加了过程确定性枷锁，抹杀了 AI 探索更优架构的自由度。
- **从路径约束撤退到系统边界约束**：
  - AI 时代的评估重心必须撤回至系统输入输出的边界；
  - 采用契约测试（Contract Testing）、属性测试（Property Testing），或引入完全独立的审计 AI 实例根据自然语言规范核对语义共识，以语义灵活性换取系统可靠收敛。

### 2. 任务自动发现的发散性局限与人类防线
- **自动需求发现的落地误区**：让 AI 全自动扫描 CI 日志或 Bug 跟踪器自行决定“下一步做什么”，在实际生产中往往沦为噱头；
- **业务上下文与战略缺失**：优先级排布需要公司的中长期战略考量、用户同理心与商业权衡，这些隐性上下文高度动态漂移，AI 极易做出与大局脱节的局部决策；
- **发散系统与架构屎山风险**：代码实现写错属于局部收敛问题（可由编译报错或测试捕获），而需求发现和架构决策是**发散系统**。一旦方向走偏，Agent 会在错误基石上持续堆砌代码，演化出无法维护的架构负债；因此“决定做什么、以什么顺序做”依然是人类不可让渡的核心防线。

## 多智能体协同进阶：图工程（Graph Engineering）拓扑编排

当系统复杂度从“单个自主循环”演进至“多个专业子循环协同（Multi-Agent Loops）”时，单纯的线性执行将面临路由失控与状态污染。**图工程（Graph Engineering）** 即利用有向图（Graph）拓扑结构对多个 Loops 进行高阶编排的工程学科：

### 核心物理要素
1. **节点（Nodes）**：代表具体的自主循环（如规划 Loop、编码 Loop、审查 Loop）或纯确定性计算节点。
2. **边（Edges）与条件路由**：定义执行顺序、并行分支合并、条件回退与跨循环断言。
3. **共享全局状态（Shared State）**：在节点间传递受严格架构约束的上下文黑板，防止不可控的状态扩散。

### 工程设计准则
- **非必要勿建图**：仅在存在明确的“角色专业分工（Specialization）”或“故障爆炸半径隔离（Failure Isolation）”时才引入图拓扑；简单的线性步骤严禁过度图工程化。
- **循环自收敛前置**：每个子节点必须首先是自收敛（Self-converging）的稳定闭环，避免发散错误沿着拓扑边放大。
