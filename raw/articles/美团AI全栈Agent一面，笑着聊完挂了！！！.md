## 美团AI全栈Agent一面，笑着聊完挂了！！！

大家好，我是Yuka。

美团的面试官是这么多场里最 **和蔼** 的一位，全程笑着聊，像在跟同事讨论技术方案而不是在面试。开场让我介绍Agent项目，我说了RAG流程，他立刻追问"如果Markdown没有标题你怎么切分""短query和长chunk向量化差异在哪"，追得很细但态度很温和。

后面给了一道AI Coding场景题，让我口述思路不用写代码，我讲完后他还帮我补充了几个我没考虑到的边界情况，感觉真的在"探讨"技术。

面完我自我感觉挺良好的，结果后来还是挂了，反馈是"项目经验与岗位匹配度不够"。可能是电商场景下的Agent经验我确实缺了点。

## 1\. 设计"智能行程规划Agent"，描述工具编排和异常处理

**我的回答** ：用户输入"周末去南京玩两天"，我设计四步流程。

第一步调 **天气API** 查南京周末天气，决定带什么衣服、哪些户外活动合适。第二步调 **酒店搜索API** ，按位置和价格范围推荐酒店。第三步调 **景点推荐API** ，结合用户偏好（美食/历史/自然）推荐景点并排行程。第四步调 **路线规划API** ，计算景点间交通时间和路线顺序。

**异常处理** ：天气API挂了就提示"天气信息暂时无法获取，建议您自行查看天气预报"。酒店API返回空就扩大搜索范围再查一次。某一步失败不影响已成功部分的结果返回，部分结果也能给用户先用。

## 2\. 用户需求模糊时，如何设计多轮澄清机制？

**我的回答** ：用户说"找个好吃的"，系统不能直接搜"好吃的"。

**第一轮澄清** ：问关键维度——"您想找什么类型的餐厅？中餐、西餐还是日料？"、"您大概在什么位置？"、"您有预算范围吗？"

**第二轮追问** ：如果用户回答了但信息仍不够，继续细化——"您更看重口味还是环境？"、"需要包间吗？"

**退出条件** ：收集够4个关键信息（品类、位置、预算、人数）后自动退出澄清，开始执行搜索。 **超时兜底** ：用户3轮都不回答就给出默认推荐（热门高分餐厅），不无限追问。

## 3\. RAG中召回结果不相关，如何优化Query Rewrite？

**我的回答** ：短query对长chunk语义匹配天生不友好，因为query信息密度低，很难精准匹配到chunk里的具体内容。

**改写方向** ：把短query扩展成更具体的描述。用户问"怎么退款"改写为"在美团App上申请订单退款的完整操作步骤"，用更完整的表达去匹配文档里的内容。用户问"有什么推荐"改写为"根据当前热门榜和我的口味偏好推荐几家餐厅"。

**改写策略** ：用历史成功检索的query做样本训练一个小模型专门做改写，或者让大模型先生成多个候选改写用检索结果质量做反馈选最优的。

## 4\. 如何保证Agent输出的JSON符合下游要求？

**我的回答** ：用 **Schema校验** 做强制约束。

在Prompt里明确告诉模型"必须输出以下格式的JSON"，附上完整的JSON Schema定义（字段名、类型、必填/可选、枚举值）。模型输出后先用 `jsonschema` 库校验，校验不通过就触发"格式修正"——把错误信息反馈给模型让它重新生成，最多重试2次。重试仍失败就返回友好错误提示。

**追问** ：如果模型反复输出错误格式怎么办？回答：检查Prompt是否清晰，或者改用 `response_format={"type": "json_object"}` 强制约束输出格式。再不行就降级到正则解析做后处理容错。

## 5\. 如何实现Agent的"记忆压缩"？

**我的回答** ：核心是"保留决策信息，丢弃过程信息"。

每次对话结束后，用LLM提取本轮对话的关键信息——用户说了什么、Agent做了什么决策、产生了什么结果、有哪些待办事项。提取结果存成结构化摘要（JSON格式），替换掉原始对话文本。

**触发器** ：对话轮次超过10轮或token数超过上下文窗口的60%，触发一次压缩。压缩后保留摘要+最近3轮完整对话。这样上下文长度减半但关键信息还在。

**追问** ：压缩会不会丢失信息？回答：设计上只压缩"已完成"的轮次，正在进行的任务上下文不压缩。

## 6\. 设计"商品推荐Agent"，评分公式怎么设计？

**我的回答** ：综合评分公式 = 用户画像匹配度×0.4 + 实时行为×0.3 + 库存×0.2 + 新鲜度×0.1。

**用户画像匹配度** ：用户历史购买品类、价格区间偏好、品牌偏好与当前商品的embedding余弦相似度。 **实时行为** ：近1小时点击、加购、收藏行为加权得分，点击1分、收藏3分、加购5分，衰减因子让越近的行为权重越高。 **库存** ：库存充足得满分10分，库存<10件得0分（不推荐缺货商品）。 **新鲜度** ：上架时间，新商品得分高，超过30天逐渐衰减。

Agent每10分钟重新算一次分，保证推荐结果实时更新。

## 7\. 如何对Agent做压力测试？

**我的回答** ：用 **逐步加压法** 找系统极限。

用wrk或locust模拟并发用户，从10并发开始，逐步增加观察QPS、延迟（P50/P95/P99）、错误率变化。 **QPS** 平稳上升直到某个点不再增长（系统瓶颈）， **P99延迟** 超过SLA阈值（如2秒）时达到极限， **错误率** 超过1%时服务已过载。

最佳并发数是P99延迟开始急剧上升的前一个点。压力测试还要模拟 **突发流量** ——10秒内并发从10飙升到1000，看系统能不能扛住而不雪崩。

## 8\. 代码生成场景中，如何保证生成的代码没有安全漏洞？

**我的回答** ：三道防线。

**代码审查** ：用Semgrep或SonarQube做静态分析，检测SQL注入模式、命令注入模式、硬编码密钥、不安全的反序列化等常见漏洞。命中规则就标记为高危，不交付。

**沙箱执行** ：生成的代码在隔离环境里跑一遍单元测试，验证功能正确性的同时检测运行时有没有危险行为（访问敏感文件、发起外部网络请求等）。

**人工复核** ：高风险代码（涉及支付、权限、用户数据）必须人工review才能合入。

## 9\. 如何设计"Agent自我评估"模块？

**我的回答** ：让Agent对自己每步决策输出置信度分数。

每次Action之前，Agent输出一个 `confidence` 字段（0-1之间的浮点数）。不同置信度走不同流程—— **高于0.85** 直接执行， **0.5-0.85** 触发"二次确认"（Agent再想一遍验证决策合理性，必要时补充检索）， **低于0.5** 不执行，直接向用户澄清。

**追问** ：置信度分数本身不可靠怎么办？回答：结合工具返回结果做验证。工具返回成功且结果符合预期，说明决策是对的。工具返回失败或结果异常，即使置信度高也要重新思考。

## 10\. 用户中途取消长任务时，如何安全终止子任务？

**我的回答** ：每个子任务分配 `task_id` ，用全局取消标记控制。

用户取消时调用 `cancel(task_id)` 标记取消。子任务的执行循环每一步检查标记，检测到取消就执行清理（关闭文件句柄、释放锁、回滚部分操作）后安全退出。

**关键点** ：不强行中断正在执行的同步操作（避免资源泄漏），而是检查取消标记后优雅退出。对于长时间阻塞的操作（如API调用），用 `asyncio.wait_for` 设超时，超时后检查取消状态再决定是否继续。

## 11\. 你了解Redis分布式锁吗？并发场景下如何避免死锁？

**我的回答** ：用 `SET key value NX EX 30` 加锁，释放用Lua脚本校验value再删除。

**避免死锁** ：设置锁过期时间防止进程崩溃后锁永不释放。获取锁时设一个"获取超时"（如3秒），超时获取不到就放弃，避免线程无限等待。使用Redisson的Watch Dog机制自动续期，业务执行完显式释放锁。业务执行完必须 `finally` 块释放，任何异常都不能跳过释放操作。

## 12\. 手撕：检测括号字符串是否有效

**我的回答** ：现场写了栈解法。

```
public boolean isValid(String s) {
    Stack<Character> stack = new Stack<>();
    Map<Character, Character> pairs = Map.of(')', '(', ']', '[', '}', '{');
    
    for (char c : s.toCharArray()) {
        if (pairs.containsKey(c)) {
            if (stack.isEmpty() || stack.pop() != pairs.get(c)) return false;
        } else {
            stack.push(c);
        }
    }
    return stack.isEmpty();
}
```

遇到右括号检查栈顶是否匹配，匹配则弹出，不匹配返回false。遇到左括号入栈。最后栈空说明全部匹配。

## 13\. 系统设计：Agent的"插件系统"如何支持热插拔新Skill？

**我的回答** ：核心是"工具注册中心"加"动态加载"。

每个Skill是独立Python模块，实现统一的 `Tool` 接口（ `name` 、 `description` 、 `schema` 、 `execute` ）。模块放在 `/plugins` 目录下，启动时扫描注册到工具注册中心。

**热插拔** ：文件变更监听（watchdog）检测到新文件或文件修改，自动加载新模块替换旧的注册信息。版本号控制让新旧请求不打架——新请求用新版本，存量请求完成后再卸载旧模块。

## 14\. 如何对Agent做A/B测试？

**我的回答** ：把用户随机分两组，A组用旧Prompt，B组用新Prompt，跑一段时间对比效果。

**核心指标** ：任务完成率、用户满意度（评分/反馈）、平均对话轮数、每次任务成本。 **观察周期** ：至少7天（覆盖工作日和周末的用户行为差异），样本量每组至少1000个有效会话。

**判断规则** ：新Prompt在任务完成率上显著优于旧Prompt（p<0.05），且成本和延迟没有显著劣化，就全量切换到新Prompt。

## 15\. 在对话中如何避免"角色混淆"？

**我的回答** ：用 **System Message和User Message明确区分** 。

用户问题放在 `role="user"` 里，系统指令放在 `role="system"` 里，Agent自己的推理和行动指令放在 `role="assistant"` 里。工具返回结果放在 `role="tool"` 里，消息结构清晰分离。

**设计原则** ：System Message里写"你是一个XX助手"不写具体任务指令，具体任务指令放在每轮User Message的开头。这样用户再怎么输入，模型也能分清楚哪些是系统给的边界、哪些是用户说的内容、哪些是自己生成的。

## 16\. MCP和Skill的区别是什么？

**我的回答** ： **MCP是标准协议** ， **Skill是具体实现** 。

MCP定义"怎么调工具"——协议格式、通信方式、错误处理规范。Skill是"具体调什么工具"——查询数据库、调用API、执行代码的具体逻辑。

**使用场景** ：需要跨Agent复用的通用工具（搜索、计算、翻译）用MCP实现，一次实现处处可调。业务相关的、领域特定的工具（电商查询、库存管理）用自定义Skill，灵活度高。

## 17\. 如何设计Agent的"回滚"机制？

**我的回答** ：每步操作记录"操作日志"——操作类型、操作参数、操作前的状态快照。

**触发回滚** ：Agent执行了非法操作、用户明确要求撤销、或者产生了不可预期的副作用时触发回滚。回滚执行反向操作——写操作调对应的"撤销"接口、删除操作从回收站恢复、修改操作用状态快照覆盖。

**关键设计** ：操作日志不能只记"做了什么事"，还要记"做这件事之前的状态是什么"，才能完整恢复到之前的状态。

---

## 18\. 如何统计Agent的"任务完成率"？如何避免人工评估的主观性？

**我的回答** ：主观完成率加上客观验证机制，只靠用户点"解决了"不准确。

**客观验证** ：用户问"查天气"就验证工具调用是否返回了有效的天气数据。用户问"生成报告"就验证报告是否包含所有必要章节。用户问"计算1+1"就验证输出里是否包含"2"。

**综合评估** ：客观验证通过率（权重70%）+ 用户主动确认（权重20%）+ 人工抽检（权重10%）加权得到任务完成率，比单一指标更可靠。

## 19\. 在Agent中集成多模态，如何融合视觉和文本信息？

**我的回答** ：视觉信息通过 **多模态编码器** 转成向量后注入文本空间。

图片用CLIP或类似模型提取视觉embedding，通过投影层映射到LLM的embedding空间，作为特殊token序列拼接到文本token之前一起送进LLM。LLM在生成文本时可以"看到"图像信息，实现图文联合理解。

文本和图像之间的"桥"是投影层——一个可训练的MLP或Q-Former，把图像特征转成LLM能理解的格式。如果是多图输入，每张图独立编码后拼接。

## 20\. 手撕：找出数组中第k大的元素

**我的回答** ：现场用快速选择算法实现，平均O(n)时间复杂度。

```
public int findKthLargest(int[] nums, int k) {
    return quickSelect(nums, 0, nums.length - 1, nums.length - k);
}

private int quickSelect(int[] nums, int left, int right, int k) {
    if (left == right) return nums[left];
    int pivotIndex = partition(nums, left, right);
    if (k == pivotIndex) return nums[k];
    else if (k < pivotIndex) return quickSelect(nums, left, pivotIndex - 1, k);
    else return quickSelect(nums, pivotIndex + 1, right, k);
}
```

原理：快排思想，每次partition把小于pivot的放左边、大于pivot的放右边，pivot落到正确位置。如果pivot位置正好是k就返回，否则递归只搜一半。平均O(n)，最坏O(n²)。
