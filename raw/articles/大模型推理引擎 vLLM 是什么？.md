## 导语

部署大语言模型后，线上推理系统的性能瓶颈往往集中在三个方面：**显存碎片与预留浪费**、**自注意力机制中的重复计算**，以及**并发请求下的排队阻塞**。

理解高吞吐推理引擎 vLLM 的工作原理，最适合的切入点就是自回归模型逐 token 生成时所保存的 **KV Cache**。在此基础上，进一步理清 vLLM 如何将内存块管理、请求调度策略与底层 GPU 并行执行有机连接起来，就能全面掌握大模型推理服务的核心优化脉络。

## 1. 先看 KV Cache 为什么占显存（00:00 - 03:02）

把大模型权重加载进显卡，再对外暴露 HTTP 接口，即可开始响应用户提问。但在原生“逐个处理请求”的朴素模式下，并发量一旦上升，后续请求就只能陷入漫长的排队等待。vLLM 作为专为大模型设计的推理服务引擎，核心职责就是通过**精细化管理显存、智能组织批量计算、动态调度请求**，大幅提升同一批 GPU 的算力与显存利用率。

### 1.1 缓存省计算，但也极其消耗显存空间

大语言模型是以自回归方式逐个生成 token 的（token 是模型处理文本的基本单元，可以是一个字、一个词或部分英文单词）。在生成新 token 时，自注意力（Self-Attention）机制必须参考前文所有 token 的 Key（K）和 Value（V）两组向量数值。

- **减少重复计算**：前文各 token 对应的 K、V 向量计算完毕后，可以缓存在显存中，后续步数直接读取即可，这份显存结构就是 **KV Cache**。例如生成第 500 个 token 时，只需参考前 499 个 token 已经缓存的 KV，无需重头将前文重算一遍。
- **显存随序列线性膨胀**：虽然避免了重复计算，但 KV Cache 会随着生成序列长度的增长而持续吞噬显存。以 **LLaMA-13B** 模型为例，一个上下文长度为 2048 token 的单次请求，其 KV Cache 就要占用约 **1.6 GB** 显存。当并发数十上百个请求时，KV Cache 的开销甚至会迅速超越模型权重本身。

### 1.2 朴素预留机制的困境

在传统推理框架中，由于每个请求最终会生成多少 token 是事先未知的，系统通常会为请求静态预留上限空间，从而带来两大顽疾：

- **预留过多（内部碎片）**：如果系统按最坏情况为每个请求预留 2048 个 token 的连续显存空间，而用户实际只输出了 200 个 token 便提前停止，剩下的 1800 多个 token 对应的显存位置就会被完全闲置并白白浪费。
- **空间碎片难以分配（外部碎片）**：即使当前显存池的空闲显存总量看起来十分充足，但由于物理显存已经被切得零散，往往难以找到一段足够长的、连续的显存空间来承载一个长上下文新请求。结果新请求只能被迫等待前面已有请求彻底执行完毕并整块释放显存。

## 2. 分块存储，再复用共同前缀（03:03 - 06:02）

### 2.1 借鉴虚拟内存思想：PagedAttention 与块表机制

操作系统的虚拟内存（Virtual Memory）为解决内存碎片提供了成熟的工业界思路：程序看到的是一段连续的虚拟内存地址，而在底层硬件层面，数据可以被切分成固定大小的“物理页”分散存放在物理内存的任意角落，操作系统通过维护一张“页表（Page Table）”记录虚拟页到物理页的映射关系。

vLLM 提出的核心技术 **PagedAttention** 将该思想迁移到了大模型 KV Cache 管理中：
- 逻辑上连续的 KV Cache 被划分为固定大小的**逻辑块（Block）**（例如每个块固定容纳 4 个或 16 个 token 的 KV 向量）；
- 在物理显存中，各个块可以**完全离散、非连续地存放**；
- 逻辑顺序由系统的**块表（Block Table）**进行映射和维护；
- 执行注意力计算时，底层算子直接根据块表寻址，跳转到对应的物理显存块进行读取。

| 逻辑内容 | 示例（每块容纳 4 个 token） | 如何读取或扩展 |
| :--- | :--- | :--- |
| **第一个逻辑块** | 保存 token 1～4，已完全写满 | 块表直接指向其实际物理显存位置 |
| **第二个逻辑块** | 保存 token 5～7，剩余 1 个空位 | 新生成的下一个 token 写入该空位；其物理块在显存中无需与第一块相邻 |
| **后续动态增长** | 当前逻辑块写满后，再动态向显存池申请下一块 | 更新块表映射，模型继续按逻辑顺序寻址访问 |

通过这种分页管理方式，每个请求在生命周期内**最多只会在最后一个未写满的物理块中浪费少量位置**，固定大小的块设计从根本上消除了显存分配中的外部碎片。同时，所有显存块被置于全局统一管理的显存池中，按需领取、用完即归还复用，大幅减少了反复向 CUDA 申请和释放显存的昂贵开销。

### 2.2 共同前缀不必重复计算：前缀缓存（Prefix Caching）

在实际线上应用中，大量用户请求往往共享相同的系统提示词（System Prompt），例如统一以 `“你是一个专业设计师...”` 开头。

vLLM 引入了**前缀缓存（Prefix Caching）**机制：
- 系统为每一个已经写满 token 的物理块计算哈希指纹（Fingerprint）；
- 该指纹同时涵盖了该块自身的内容以及该块之前所有前置块的完整上下文；
- 当新请求进入系统时，如果其前缀命中了已有缓存块的指纹，就可以直接挂载并复用这些已经算好的 KV 显存块，**彻底免去了重复计算前缀注意力与重复占用显存的代价**。

> **💡 业务工程实践提示**：
> 在设计提示词模板时，**将固定的系统设定、范例等静态内容前置，将用户动态变化的提问内容后置**，能够显著提升前缀缓存的命中率。

## 3. 让短请求及时离场，长输入分段处理（06:03 - 07:59）

在通过 PagedAttention 解决显存利用率后，推理引擎面临的下一个核心挑战是：**如何将多并发请求高效打包送入 GPU 执行？** 如果逐个处理请求，GPU 庞大的并行计算单元会长期处于空闲状态，因此必须采用批处理（Batching）技术提升吞吐。

### 3.1 静态批处理 vs 连续批处理

- **静态批处理（Static Batching）**：系统凑齐一批（Batch）请求后统一送入 GPU，必须等待整批中**生成序列最长的那一个请求彻底结束**，才能换下一批。如果一个请求只要生成 10 个 token，而另一个请求需要生成 500 个 token，短请求在生成完 10 个 token 后，其占据的槽位只能空转等待，无法提前离场，新请求也无法插入，GPU 计算资源被严重浪费。
- **连续批处理（Continuous Batching / 迭代级调度）**：vLLM 采用迭代级（Iteration-level）粒度的动态调度。模型每生成一个 token，调度器就重新做一次调度决策。已经生成结束的请求立即离场并归还其占用的显存块；新到达的请求可以在下一个迭代步立即插队加入当前批次。调度器动态掌管每一步“谁进、谁出”。

### 3.2 长输入的分块预填充（Chunked Prefill）

在连续批处理中，系统仍会遇到新的性能扰动：处理一个拥有几千甚至上万 token 的长 Prompt（即 Prefill 预填充阶段）需要巨大的矩阵乘法计算量，可能会在单步内长时间霸占 GPU 算力，导致同一批次中其他正在逐 token 输出（Decode 阶段）的用户请求产生明显的中途卡顿。

为了平衡首字延迟与输出流畅度，vLLM 引入了**分块预填充（Chunked Prefill）**：
- 将超长的 Prompt 拆切为若干个固定大小的小分块（Chunks）；
- 分多轮逐步完成预填充计算，在不同轮次之间穿插其他用户的生成步；
- **每轮处理 token 较少**：解码请求更少被打断，输出体验更加流畅细腻；
- **每轮处理 token 较多**：Prefill 阶段的计算密度更高，首字响应时间（TTFT）更快、整体吞吐（Throughput）更高（在追求极致吞吐的高吞吐场景下，官方建议可考虑将每轮 token 预算设置为 8192 以上）；
- **限制并发序列数**：除了配置每轮最大 token 预算外，还可以结合限制单步最多处理的并发序列数，实现对批次计算规模的双重约束。

## 4. 模型装不下时：量化、卸载与多卡并行（08:04 - 10:34）

当模型参数体量过大、单张显卡物理显存无法完全装下时，通常有三种技术路径：**模型量化**、**CPU 内存卸载**与**多卡分布式并行**。

### 4.1 权重量化与 KV Cache 降精度

大模型权重本质上是一组高维浮点数。量化通过降低数值的存储位宽，达到大幅削减显存需求的目的：
- **权重量化**：例如将参数从 FP16（每个数值占 2 字节）降到 FP8（每个数值占 1 字节），模型权重占用的显存直接减半。同时低精度张量算子还能提升计算吞吐，代价是可能会产生微弱的精度损失。实际工程经验表明，现代模型的 FP8 量化通常能在带来显著性能提升的同时，将精度损失控制在极小范围内。vLLM 支持自动识别已量化模型权重，也支持在启动阶段将原始模型在线转为 FP8 格式。
- **KV Cache 降精度（FP8 KV Cache）**：不仅权重可以量化，KV Cache 同样可以压缩至 1 字节。采用 FP8 KV Cache 后，相同显存容量能够容纳的 token 总量几乎可以翻倍，从而成倍扩大并发承载上限。

### 4.2 CPU 内存卸载（CPU Offloading）及其权衡

将部分模型层或计算中间状态放置在主机内存（RAM）中，在需要执行该层计算时再通过 PCIe 总线临时搬运至 GPU 显存。例如在显存告急时借用 20 GB 系统内存。
- **局限性**：受制于 PCIe 通道有限的带宽，数据频繁在 CPU 内存与 GPU 显存之间搬运极其耗时，会导致端到端推理延迟大幅飙升。因此 CPU Offloading 通常仅适合个人低成本本地体验，面向生产级对外服务时，工业界依然倾向于采用多卡部署。

### 4.3 多卡并行拆分方式：张量并行 vs 流水线并行

在多卡部署场景下，模型权重的切分方式主要有两大主流范式：

| 拆分方式 | 模型如何分配 | 主要代价与适用场景 |
| :--- | :--- | :--- |
| **张量并行 (Tensor Parallelism, TP)** | 将模型内部每一层的计算和权重矩阵按切片分摊给多张 GPU 卡，各卡并行计算一部分。 | 每一层计算完毕后，多卡之间需要执行频繁的高频卡间同步通信（如 All-Reduce）。**适用于具备高速互联环境（如单机多卡 NVLink、NVSwitch）的物理节点**。 |
| **流水线并行 (Pipeline Parallelism, PP)** | 将整个模型的网络层按层切段（例如 80 层的模型平均切为 4 段，每段 20 层分别放置在 4 张卡上），请求像流水线一样依次流经各卡。 | 仅在不同阶段交接处需要传递隐层激活值，节点间通信量较小；但请求必须依次经过各个计算段，且流水线前后存在“气泡”，**单请求端到端延迟通常会更高一些**，更适合跨节点或缺乏高速互联的多机环境。 |

### 4.4 只是请求太多？果断采用数据并行（Data Parallelism, DP）

若单张 GPU 显存已经能够完整容纳整个模型权重与适量上下文，但线上并发请求数巨大导致排队严重，此时**无需对模型进行切分**（切分反而引入跨卡通信开销）。

直接配置 `--data-parallel-size` 启动多个模型副本：
- 例如配置 `--data-parallel-size 4`，系统会在 4 张卡（GPU 0、GPU 1、GPU 2、GPU 3）上分别加载一个完整模型独立运行；
- 外部并发请求通过内部路由自动负载均衡到各个副本，线性扩展系统的整体吞吐量。

## 5. 一个请求如何穿过 vLLM（09:13 - 12:07）

从系统软件架构视角来看，vLLM 内部主要分为三层协作核心：
- **API Server**：最外层接入服务，负责对外暴露标准网络接口（原生兼容 OpenAI API 格式），解析用户请求并执行分词（Tokenization）；
- **Engine Core**：系统大脑与集中管控中心，负责全局请求队列调度、显存块分配、前缀指纹匹配、长 Prompt 分段管理以及显存抢占；
- **GPU Worker**：底层的具体执行节点，负责加载切分后的模型权重并执行 GPU 算子计算（通常一个 GPU Worker 独占绑定一张物理 GPU）。

```
+-------------------------------------------------------------+
|                         API Server                          |
|             (兼容 OpenAI 协议接口、Token 切分)              |
+-------------------------------------------------------------+
                               |
                               v
+-------------------------------------------------------------+
|                        Engine Core                          |
|     (调度器 / PagedAttention 块表管理 / 前缀缓存 / 抢占决策)|
+-------------------------------------------------------------+
                               |
                               v
+-------------------------------------------------------------+
|                        GPU Workers                          |
|      Worker 0 (GPU 0)   |   Worker 1 (GPU 1)   |   ...      |
|      (权重加载、注意力算子执行、逐 Token 计算推进)          |
+-------------------------------------------------------------+
```

### 请求端到端执行四部曲

1. **第一步：接入并准备请求**  
   用户发起的 HTTP 提示词请求到达 API Server，文本被分词器切分成 token 序列并提交给 Engine Core。调度器首先检索前缀缓存（Prefix Caching），若存在共享的前置文本块，则直接建立块表复用；对于其余未命中部分，调度器按需从全局显存池中分配初始的逻辑块。
2. **第二步：与其他请求共同计算**  
   连续批处理调度器将该请求与当前批次中其他处于就绪态的活跃请求编入同一个计算步骤（Step），统一下发给底层的 GPU Worker 矩阵并发执行。
3. **第三步：逐 Token 推进生成**  
   GPU Worker 执行模型注意力计算，算子直接依据当前请求的块表寻址并读取离散分布在显存中的历史 KV 数据。当前步新采样生成的 token 会被追加到序列末尾，成为下一步迭代计算的新输入；当某个物理块被完全写满后，系统动态向显存池申领下一个空闲块。
4. **第四步：结束并释放资源**  
   当某个请求生成了终止符（`[EOS]`）或达到了最大生成长度上限，该请求立即宣告结束并退出当前批次，其所持有的全部物理显存块被瞬间归还至全局显存池，供后续排队的其他请求循环复用。

## 6. 先看指标，再决定调哪里（04:30 - 12:44）

在生产高并发环境下，当突发流量导致 GPU 显存块耗尽时，处于生成阶段的活跃请求可能无法成功申请到新的 KV 块。此时 vLLM 会触发**抢占机制（Preemption）**（例如暂停部分低优先级请求的生成，将其 KV 状态临时驱逐甚至重算），以腾出空间保证其他请求正常执行。

通过 vLLM 提供的监控指标接口（Prometheus Metrics），可以精准定位系统当前的性能与显存瓶颈：
- **KV Cache 使用率（`vllm:gpu_cache_usage_factor`）持续接近 1.0**；
- **等待队列中持续存在排队请求（`vllm:num_requests_waiting > 0`）**；
- **抢占次数指标持续上升（`vllm:num_preemptions` 频繁增加）**。

一旦观察到上述瓶颈信号，即可对照下表进行针对性参数调优：

| 观察到的现象 | 可采取的调优动作 | 核心参数/机制 | 作用机理与权衡取舍 (Trade-offs) |
| :--- | :--- | :--- | :--- |
| **缓存紧张、频繁发生抢占** | 适度调高 GPU 显存分配比例 | `--gpu-memory-utilization` | 为 KV Cache 块管理池开辟更大的显存水位，提升并发承载力。默认通常为 0.9，若显存充足且无外部进程干扰，可酌情上调（如 0.95）。 |
| **实际业务不需要超长上下文** | 调低单次请求输入与输出总长度上限 | `--max-model-len` | 严格限制极长请求的产生，使单位显存能够容纳更多标准请求。设置必须满足实际业务的最大长度需求。 |
| **显存池容量依然存在瓶颈** | 开启低精度 KV Cache | `--kv-cache-dtype fp8` | 通过将 KV Cache 的数值精度由 16 位压缩至 8 位，使单 token 显存开销直接减半，容量翻倍。 |
| **前缀缓存命中率低下** | 调整系统提示词结构顺序 | Prompt Engineering | 将全局公共固定内容前置，将用户提问或高频变动变量后置，促使系统最大化命中前缀缓存。 |
| **解码输出频繁被长输入打断** | 开启分块预填充，精细调优 token 预算与并发数 | `--enable-chunked-prefill`<br>`--max-num-batched-tokens`<br>`--max-num-seqs` | 将长 Prompt 切段分批消化，在保持输出流畅度、首字响应延迟（TTFT）与系统吞吐量之间取得最佳工程平衡点。 |

### 调优总结

大模型推理系统的各项优化手段针对着不同的资源开销：
- **前缀缓存复用** 削减的是前文的**重复计算开销**；
- **PagedAttention 分块管理** 消除的是显存碎片，最大化**显存空间利用率**；
- **连续批处理与 Chunked Prefill** 盘活的是 GPU 算力的**高并发并行能力**；
- **量化与低精度编码** 压缩的是参数和上下文的**物理体积**。

在实际生产运维中，只有从线上实际采集到的排队等待数、抢占频率、前缀命中率与 KV Cache 水位等客观指标出发，有的放矢地调整对应参数，才能真正实现高吞吐、低延迟的推理加速目标。

## 7. vLLM Serve 核心参数速查与生产实战运维

在工业界落地中，通常使用 `vllm serve` 命令启动 OpenAI 兼容的服务端。以下基于 **vLLM v0.31.0** 标准，系统梳理常用参数与生产运维调优实践。

### 7.1 标准生产启动命令范式

```bash
vllm serve \
  --model Qwen/Qwen3-14B \
  --served-model-name qwen3 \
  --gpu-memory-utilization 0.92 \
  --host 0.0.0.0 --port 8000 \
  --api-key sk-xxxxxx
```

### 7.2 核心参数分类速查表

#### 1. 必知核心参数（大多数场景必须配置）
| 参数 | 管的是什么 | 默认值 | 生产建议 |
| :--- | :--- | :--- | :--- |
| `--model` | 实际加载的模型路径或 HuggingFace/ModelScope 模型名称 | 无（**必填**） | 填写绝对路径或官方模型标识符 |
| `--served-model-name` | 接口对外暴露的模型名称 | 与 `--model` 一致 | 简化对外名称（如 `qwen3`），需与客户端请求的 `model` 字段严格一致 |
| `--max-model-len` | 上下文长度（Prompt + 输出的最大上限） | 模型自身最大长度 | 若业务场景不需要极长上下文，主动调低（如 4096/8192）以节省显存 |
| `--gpu-memory-utilization` | 给当前 vLLM 实例分配多少显存比例 | 0.92 | 单卡独占通常设 0.90～0.95；多卡或存在常驻进程时需按需降低 |
| `--tensor-parallel-size` | 几张卡一起分摊每一层（张量并行 TP） | 1 | 模型大于单卡显存时使用（如 2、4、8 卡），需配合 NVLink 高速互联 |
| `--max-num-seqs` | 一步最多同时计算几个请求并发序列 | 按显卡 256 或 1024 | 配合显存与 Token 预算防止过载崩溃 |
| `--max-num-batched-tokens` | 一步最多处理多少个 Token | 按显卡与用法自动定 | 吞吐优先场景可调大至 8192 以上 |

#### 2. 日常推荐参数（大部分场景用默认值即可）
| 参数 | 管的是什么 | 默认值 | 说明与建议 |
| :--- | :--- | :--- | :--- |
| `--quantization` | 权重显存量化方式（如 awq, gptq, fp8） | 读模型配置 | 已量化模型自动识别；原版权重也可指定 fp8 在线量化 |
| `--kv-cache-dtype` | KV Cache 存储精度格式 | 跟随模型（默认 auto） | 显存告急时可指定 `fp8`（如 `fp8_e4m3`），单 token 缓存减半 |
| `--dtype` | 权重加载与执行计算的数据类型 | auto | 默认跟随模型（支持 bfloat16/float16）；老卡（如 V100/T4）自动安全回退至 float16 |
| `--enable-prefix-caching` | 是否开启前缀缓存（Prefix Caching） | 模型支持就开 | 强烈建议开启，显著提升共享系统提示词的复用率 |
| `--enable-chunked-prefill` | 是否开启分块预填充（长 Prompt 切段） | 模型支持就开 | 长短混合请求并发时建议开启，防止长输入打断解码 |
| `--block-size` | 一个 PagedAttention 显存块放几个 Token | 按显卡与模型自动选 | 常用 16 或 32 |

#### 3. 场景按需调整（多卡、显存不足与特殊功能）
| 参数 | 管的是什么 | 默认值 | 说明与建议 |
| :--- | :--- | :--- | :--- |
| `--data-parallel-size` | 启动几份完整模型副本分摊请求（数据并行 DP） | 1 | 单卡放得下且单纯高并发请求过多时使用 |
| `--pipeline-parallel-size` | 模型按层切分成几段流水线（流水线并行 PP） | 1 | 跨机节点缺乏 NVLink 互联时使用 |
| `--cpu-offload-gb` | 借用多少 GB 的 CPU 主机内存存放权重 | 0 | 显存不够且预算有限时尝试（个人尝鲜为主，通信较慢） |
| `--kv-cache-memory-bytes` | 直接以字节数指定 KV Cache 显存容量 | 不设（自动算） | 特殊固定显存分配场景使用 |
| `--enforce-eager` | 是否禁用 CUDA Graphs 录图（强制 Eager 模式） | 关（默认录图） | 开启后**不录图，能省少量显存**，但推理吞吐会变慢 |
| `--trust-remote-code` | 是否允许执行模型仓库自定义 Python 代码 | 关 | 加载部分第三方新架构模型时需开启 |

#### 4. 对外服务与协议适配参数
| 参数 | 管的是什么 | 默认值 | 说明与建议 |
| :--- | :--- | :--- | :--- |
| `--host` | 服务的监听网卡地址 | 所有网卡（0.0.0.0） | 容器化部署或公网暴露使用 |
| `--port` | 服务的监听端口 | 8000 | 常用默认端口 |
| `--api-key` | API 鉴权访问密钥 | 无 | **对外开放时必须配置密钥**（如 `sk-xxxxxx`），防止未授权调用 |
| `--enable-auto-tool-choice`| 允许服务端代模型决策工具调用参数 | 关 | 结合 Agent Tool Calling 场景开启 |
| `--tool-call-parser` | 工具调用解析器 | 不设 | 指定如 `hermes`、`mistral` 等解析器适配模型工具输出 |
| `--reasoning-parser` | 思考模型（如 DeepSeek-R1 等）思维过程提取 | 不设 | 将 `<think>` 思维链单独拆分至 reasoning_content 字段 |

> ⚠️ **已废弃参数提示**：早期版本中的 `--swap-space`（管理换出至 CPU 的内存大小）在新版本中**已被完全删除**，显存换出改由专用分离缓存层接管。

### 7.3 六大高频部署实战避坑指南

1. **模型名必须对齐**：`--model` 是本地权重目录或标识，`--served-model-name` 是 API 接口里对外展示的名字；客户端请求里的 `model` 必须与 `--served-model-name` 完全一致，否则接口直接返回 404 Model Not Found。
2. **对外暴露切记加密钥**：当使用 `--host 0.0.0.0` 开放局域网或公网访问时，必须同步加上 `--api-key sk-xxxxxx`，否则任何能触达该 IP 的客户端均可直接无限制消耗 GPU 算力。
3. **单卡放得下且请求太多用数据并行**：若单卡显存能装下完整模型，瓶颈只是排队请求过多，不要使用张量并行，直接用 `--data-parallel-size`（起多份完整模型副本分摊并发流量）。
4. **显存不足启动报错时“看末尾数字”**：当启动遇到如下经典报错：
   ```text
   ValueError: To serve at least one request with the model's max seq len (32768), ... the estimated maximum model length is 8192.
   ```
   直接查看报错末尾的数字（如 8192），将 `--max-model-len 8192`（或略小值）显式写入启动命令，即可在当前显存条件下成功启动。
5. **CUDA Graphs 录图与 `--enforce-eager` 权衡**：
   - 默认（录图）：先把模型前向图录制成静态图，显著降低 CPU 算子发射开销，推理速度最快，但会额外多占用数百 MB 显存；
   - 开启 `--enforce-eager`：跳过录图直接前向，能省下这一小部分显存，代价是推理吞吐下降。
6. **数据类型 `--dtype` 自动降级机制**：默认 `auto` 会自动读取并适配模型权重精度；当遇到 V100、T4 等不支持 `bfloat16` 硬件指令的老显卡时，vLLM 会自动回退至 `float16`，通常无需人工手动强制指定。

### 7.4 关键监控指标（`/metrics`）与前缀命中率计算

vLLM 原生提供 Prometheus 监控端点（`GET /metrics`），线上可通过以下指标实时掌握运行水位：

- `vllm:kv_cache_usage_perc`：当前 GPU KV Cache 显存使用率（逼近 100% 意味着显存饱和）；
- `vllm:num_requests_waiting`：当前排队等待调度的请求数量；
- `vllm:num_preemptions_total`：累计发生的请求抢占（Preemption）次数；
- `vllm:prefix_cache_hits_total`：累计命中的前缀缓存次数；
- `vllm:prefix_cache_queries_total`：累计发生的前缀缓存查询总数。

$$ \text{前缀缓存命中率} = \frac{\text{prefix\_cache\_hits\_total}}{\text{prefix\_cache\_queries\_total}} $$
