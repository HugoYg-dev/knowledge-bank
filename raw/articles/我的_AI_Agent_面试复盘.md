## 1. 开场：不同公司，收敛到同一套能力 `00:00 - 03:03`

作者正处在秋招阶段，面的岗位集中在 AI Engineer 和 AI Application 相关方向。最初的动机只是把之前的笔记整理一下，看看哪里答得不好，整理到最后却发现了一件有意思的事：**这几家公司的业务其实完全不一样，但它们问的问题收敛到了同一套能力上。**

### 题目在变难
四五月的时候，大部分面试官还在问 RAG、LangChain/LangGraph、prompt、MCP 这些；到了秋招阶段，作者能明显感觉到问题开始变难，出现了不少更细的追问：
* RAG 文档怎么切、为什么这么切；
* 向量数据库怎么选、数据量扩大怎么办；
* 为什么需要 multi-agent，普通 pipeline 为什么不行；
* Graph 的状态怎么存；
* Kafka 的消息为什么会堆积；
* 以及 AI Coding 类的题目。

**AI Coding 的形式是**：面试官直接给一道系统设计题，让面试者在类似 Cursor 的环境里，现场带着 AI 把系统写出来。

这场分享按照几家公司的真实面试过程展开，聊面试官问了什么、作者自己的复盘，以及未来要准备 AI Agent 岗位到底应该准备些什么。作者也说明这是个人的分享和总结，欢迎在评论区批判和交流。

## 2. 小红书：把 Agent 接进客户端性能归因 `03:48 - 09:53`

这场面试不算传统的 LLM Engineer，它带有比较强的客户端、前端性能工程与 Agent 结合的特点。作者总结下来就是一句话：**AI 一定要跟业务结合。**

### 先问性能工程，再转向 Agent
前半段是相对传统的问题：之前的工作、官网重构、怎么发现性能劣化点、有没有做 A/B Test。对于 Core Web Vitals，会涉及 CLS、LCP 等指标。
随后话题转到 Agent，面试官让作者详细讲讲崩溃/故障 Agent 到底在做什么、用了哪些模型、故障怎么判断、不同 Agent 分别负责什么、最后怎么衡量效果。这部分还属于简历询问。

### 场景题：把性能归因 workflow 交给 Agent
一面没有算法题，面试官当场出了一道很真实的场景题：客户端里有很多埋点，从 APP 启动的第一阶段、第二阶段一直到用户真正看到首屏结束，中间有特别多过程，都可以通过 SQL 查出来，平时会做带版本的对比。日常的排查方式是：发现网络阶段变差，就继续往网络的细粒度指标查；发现图片加载变差，就往图片相关的指标查，最后希望完成归因。

面试官问：**如果用 Agent 把这套东西做出来，你会怎么设计？**

> 这道题的价值在于，它问的是**怎么把一个原本由工程师完成的分析 workflow 变成 Agent 化**，而不是停留在某个技术名词是什么。

作者当时的回答包含几个点：通过固定的 SQL 或 API 拿数据做数据感知，做一些异常检测，让 Agent 判断哪个阶段出现了 degradation，再结合业务知识做 root cause analysis，最后生成报告。

$$\text{感知} \longrightarrow \text{决策} \longrightarrow \text{执行} \longrightarrow \text{归因}$$
作者用这四个词来解释什么叫 Agent。

### Agent 可以没有聊天界面
很多人一提到 Agent，第一反应还是聊天框：说一句话，AI 回一句话。其实 Agent 完全可以没有聊天界面，做数据中台的同学可能更有印象，他们的 Agent 就没有聊天界面，只是作为企业内部的提醒。
放到这个场景里，Agent 可以每天凌晨自动跑，拿到昨天的性能数据，发现某个版本性能下降，自动定位到图片加载阶段，甚至早上九点给工程师发报告。作者越来越觉得，**这类能把工程师每天重复完成的 workflow 自动化的 Agent，才是企业真正愿意付钱的方向。**

### 确定的部分交给脚本，LLM 负责归因
面试官随后加了一个限制：数据一定要非常精确，因为大模型现在有很大的幻觉问题，会导致很多报表不可信。而 SQL 的查询接口其实非常固定，团队已经在尝试用 AI 写固定的 Python script，需要不同维度时改变参数，再让大模型去做归因和解释。

> **这里透露的原则：**  
> 确定性的部分不要交给 LLM。SQL 查询是确定的，Python 的聚合设计是确定的，指标变化多少也是确定的，这些没有必要让模型自由发挥。LLM 真正适合做的是理解上下文、选择分析路径，做归因的解释。

作者说，如果重新回答，他会把系统分成两部分：**一层负责数据查询等确定性工作，LLM reasoning 层负责归因之类的工作**。这个拆分在他后面的项目里已经用上，效果还可以。

### 二面：预编排，还是动态编排
二面更偏 Agent 架构。问题包括：多 Agent 的本质是不是在构建一个预编排的逻辑链，Agent 能不能做动态的逻辑链？因为现在很多 Agent demo 就是 Agent A 到 Agent B 到 Agent C 再到 finish，它严格来说和传统 workflow 有什么区别？

* **完全预编排**：所有路径、所有节点提前写死。优点是稳定可控，缺点是灵活性很差、Agent 的自主性很弱。要不要用完全预编排，取决于项目的需求。
* **完全动态编排**：相当于只告诉模型一个目标，剩下的让 LLM 去做。这样很灵活，但在生产环境里非常危险：一旦规划能力出现问题，很容易出现无限循环、成本爆炸。

作者比较认同的方案是 **controller + workflow**：核心业务逻辑用 workflow 控制，关键节点设置约束，而局部的地方（比如选择哪些工具、检索哪些信息）让 Agent 去动态判断。

> **workflow 提供边界，Agent 在边界里面获得自主性。两者不是二选一。**  
> 这个认识在四五月时让作者觉得很有价值；到现在，很多企业已经在做这件事，而且做得还可以。

## 3. 阿里：从 RAG 切片到 Kafka 的全链路追问 `09:54 - 21:11`

阿里的面试从 RAG 系统一路问到 Kafka，作者觉得比较适合正在准备 Agent Engineer 和 AI Application 方向的人参考。

### RAG：文档怎么切、为什么这么切
自我介绍讲了项目之后，面试官马上问 RAG 是怎么用的，重点落在文档怎么切片。这个时候只回答“我是根据一些文字切片”是不够的，因为紧接着就会追问为什么这么切。  
以技术手册为例，它本身有非常明显的章节结构，比如车型、故障码、故障类型。如果每 500 token 一刀切下去，可能出现上一段是故障现象、下一段才是解决办法，拆开之后 embedding 本身的语义就被破坏了。  
作者的做法是先做 **structure-aware chunking**，根据文档标题做一级拆分；如果某个 section 太长，再做滑动窗口，并保留一些元数据。

> 这才是相对完整的答案：除了说你要做什么，还要给出完整的前因后果。

### 向量库选型：考的是 trade-off
面试官接着问向量库怎么选，这是非常典型的问题。作者说自己以前面试经常犯一个错：一看到 HNSW 之类的名词，就开始背分布、背知识，但面试官真正想听的是**你的场景为什么需要它**。  
回到作者的场景：几十份技术手册、成千上万个切片、内部原型、低并发、快速迭代。这个场景根本不需要上来就搭一个重型的分布式向量数据库，轻量的方案反而更合理。未来如果需要多租户、动态更新、高并发、高可用，模型当然可以换。

> 这个问题真正考的是你的 trade-off：重点在于哪个数据库最适合你的场景，不追求所谓最好的数据库。

入职之后，作者跟当时这位面试官（也是他后来的 mentor）聊过这件事。对方看中的是你对问题的判断能力，而非你是否正确回答了这个题目，他想要的是你的思考过程。

作者觉得这跟看 AI 很像：很多时候看 AI 直接给出的回答，不如去看它的思考过程。小红书上有人问过一个问题：现在 AI 很厉害了，那它在思考的时候你在做什么？有人回答玩手机、看抖音，作者觉得这很正常，但建议大家在 AI 思考的时候去看它的思考过程，因为思考过程在某种程度上可以改变你的思路。作者的体会是，人的思路往往比较固定，不容易做全面的发散；如果只看 AI 给的结果，思路就被结果固定住了，多看足够的推导，才能形成一种思维惯式，这也算一种思维训练。

### LangGraph：state 才是核心
RAG 问完之后开始问 LangGraph，四五月时 LangGraph 还能用，现在它不是一个非常火的状态了，很多情况下用 LangChain 也能把事情讲清楚，未必非要上 LangGraph。  
面试官问了状态是什么、状态之间的流转是什么。很多人说自己用 LangGraph 做 Agent，但被追问 graph 里有什么 state 时可能就卡住了。原因是大家做 Agent 的场景不同，有些在实习中做、有些是手搓的，很多细节没办法很好地展开。

> 状态不是一个抽象的名词。比如一个诊断 Agent 里的 state，可能包括用户、车辆信息、故障码、状态结果，这些状态在不同的 node 之间不断被读取和更新，这才是 LangGraph 的核心。

很多东西要讲得很清楚，深入到细节，避免把它大而化之。掌握多个框架之后，还会发现这些框架之间存在一些共性。

### 数据库选型与后端基本功
为什么用这个数据库，本质上考的是数据模型和存储模型是否匹配。如果 Agent state 本身就非常动态，每个 workflow 的中间字段可能都不一样，document store 确实比较自然；但如果存的是账单、账户、资金流水，可能就要用另外一套选型。  
作者发现，AI Engineer 其实非常需要传统 software engineer 的能力：数据库怎么选、缓存怎么用、失败后怎么重试和恢复，这些最后都绕不开。作者很羡慕有 software engineer 经验的人，北美这边招 Agent 相关岗位也 prefer 有 experience 的人。

### multi-agent 的杀手问题
还有一个每场面试都会问的杀手问题：**你为什么一定需要 multi-agent，一个普通的 pipeline 不行吗？**  
只要简历里写了 multi-agent，就一定要准备这个问题。很多项目其实根本不需要 multi-agent。如果你的流程永远都是 input、然后调 LLM、然后 output，本质上它就是一个 pipeline；硬说是三个 Agent，反而像过度设计。有些同学为了让简历显得高大上，会把 Codex、Claude Code 魔改的东西写上去，更需要想清楚什么情况下用 multi-agent 才合理。

作者认为至少满足下面一些条件，拆 Agent 才有意义：
1. **不同的阶段需要完全不同的工具**；
2. **不同的阶段需要不同的 prompt 和上下文**；
3. **路径需要动态的分支，某个节点失败以后可以回退**；
4. **每个角色确实有比较清晰的 responsibility boundary**。

作者提醒，不要表现出“因为 multi-agent 比较高级所以我用了它”，你需要证明复杂度是业务要求带来的；自己造出来的复杂度经不起追问。

### Kafka：消息堆积与幂等
问完这些之后，面试官突然开始问 Kafka：高峰期的消息堆积怎么解决；怎么判断是真的消息堆积，还是消费者能力不足；再往下是怎么判断消费者的 CPU 不够、网络是否有瓶颈。  
作者一开始觉得这些问题非常八股，复盘时他发现，一个生产环境里的 Agent 根本不可能独立存在：它可能需要消费 event，可能要去调用十几个 tool，产生一些 trace，并通过消息队列去做 flow。如果系统流量起来，消息堆积怎么办、消息延迟怎么办、重复消息怎么办、乱序怎么办、exactly-once 做不到的时候怎么设计幂等——这些全都是 agent engineer 的问题。

> 准备 Agent 岗位的人不要只学 LLM。数据库、Kafka、缓存、并发、网络和分布式系统这些后端基础知识不能丢。

### Text-to-SQL：限制模型犯错的空间
后面面试官问了一整套 Text-to-SQL 的问题，比较有代表性。它的定义很简单：让非技术用户直接用自然语言查数据库。真正的问题在后面：一个完全不懂数据库的人说“你帮我查一下贵价商品里面卖得最好的是哪几个”，怎么理解“卖得最好”是什么意思？这就是自然语言的模糊性。  
而 LLM 最大的问题就是它特别喜欢猜，在数据库场景里猜错就是错。所以解决办法并不能只是把 prompt 写好一点，合理的逻辑是：**如果 confidence 足够高，就继续；如果存在明显的模糊，就发起 clarification（澄清）**，比如问清楚你指的是销量最高还是销售额最高。

> 一个好的 Agent 不应该什么问题都回答，它应该知道什么时候执行、什么时候拒绝、什么时候去澄清。这种能力可能比回答本身更重要。

后面还问了多表结合、字段含义怎么保证、字段描述、表之间的 relationship、业务口径，甚至对重要指标做结果校验。这些问题已经属于 schema retrieval 和元数据管理，超出 LLM 本身的能力范围。

> **一句话概括：**  
> 生产级 AI 系统的核心是**限制模型犯错的空间**；模型是否更聪明并非这里的重点。

作者对这一点很有感触。他在美国实习时用的是 Claude Code 和 Codex，而且是满配的额度；刚去实习用国产模型时，总觉得生产中的问题是模型太蠢。后来发现真正在生产时要考虑很多问题：成本、模型的边界。模型本身是不是最聪明已经不是最重要的事情，后面有 harness、有 prompt engineering，它们把模型限制在边界内，这一点可能比模型本身是否更聪明更重要。

## 4. AI Coding 轮：面试官在看你怎么使用 AI `21:12 - 24:08`

AI Coding 这一轮单独说，它是 40 多分钟的环境，是一个沙盒体验，很像 Cursor，题目是一道系统设计题：**设计一个可扩展、逻辑清晰、带有安全约束的订单状态机引擎**。题目给了一些背景、功能要求和限制条件，过程中可以使用 AI。

作者觉得，如果上来就把整个题目复制给 AI、让 AI 帮你完成，是非常危险的做法。  
这位面试官后来成了作者的同事。作者跟他聊过这一轮到底在看什么，对方说想看的是**你怎么去使用 AI**，他 care 的是交互的过程：**你的角色是一个 tech lead，你的 agent 的角色是一个 junior developer**。

### 四个考察点
1. **先自己理解问题**：你自己有没有先理解这个问题。哪怕只是一个模糊的框架，哪怕你并没有非常明确的选择，你也要自己先理解一下。
2. **会不会拆任务**：把状态机引擎拆成不同的部分，一块一块交给 AI。
3. **会不会验证 AI**：AI 写完一个模块，你有没有去读、有没有去跑 test，有没有检查边界，还是看到绿色就直接 accept。
4. **能不能解释出来**：比如你用哪种方式定义状态，和直接用 metadata 定义状态和事件，各自的优劣是什么。这些优劣问题你必须能意识到。

> 面试官真正想看的是这个设计到底是不是你自己做的决策，代码最后有没有跑起来并不是重点。

## 5. 强业务场景下的可靠性：复杂度藏在外围 `24:09 - 27:07`

这场面试给作者最大的感受是：**AI Agent 放到强业务场景之后，Agent 本身的实现可能不再是最重要的部分。**  
reliability 是 AI 工程中很大的一部分，商业化的时候会涉及资金、广告等场景，面试官特别关注**正确性、一致性、安全性、可追溯性**这些问题。

作者简历里虽然有 Agent，还是被追问了大量传统后端问题：Kafka 的消费、消费组是什么、消费者和 partition 是什么关系、消费者数量比 partition 多会怎么样、rebalance 是什么、offset 怎么提交；还有涉及资金流水的问题，比如怎么保证顺序、怎么处理重复消费。Agent 的情况很像：**LLM 本身不是确定性的，你必须要用一个系统去兜住它。**

### 项目是真工程系统，还是套了 Agent 的名字
面试官说，他觉得作者这个 Agent platform 听起来没有那么复杂，就是输入进来、Agent 判断、调 MCP、最后输出结果。作者认为这类问题在挑战你的项目到底是真的工程系统，还是只是套了一层 Agent 的名字。从摘要上看，确实可以说它就是 input $\rightarrow$ agent $\rightarrow$ tool $\rightarrow$ output，但实际生产系统的复杂度全部藏在这个箭头之中。

作者列举了这些落在箭头里的问题：
* 谁能调这个图；
* 读操作和写操作的权限是不是一样；
* 参数的合法性检查；
* 高风险操作要不要做二次确认；
* 脚本在哪里执行；
* AI 生成的一段 Python 能不能直接在生产机器里跑。

答案当然是不能，于是引出了**沙盒**：把 Agent 生成的自定义代码丢到隔离沙盒里，超时直接杀掉，访问未授权的资源就直接拒绝。这个时候，你的 Agent 才真正从一个 demo 变成了一个 system。

> Agent 工程的复杂度不在 agent loop 本身，因为 ReAct loop 可能几十行代码就写完了。真正的复杂度是它外围的问题：授权、permission、state、沙盒这些，这才是真正的 production agent。

### 后端八股不能丢
面试里还会出现很多八股问题：什么数据可以本地缓存、什么数据不能放、垃圾回收、并发下的线程稳定性问题。  
作者曾有一个错觉：做 AI 就好好做 AI 方面的东西，追最实时的热点、看最新的代码，不该去看那些八股。现在他觉得，如果你做的是 AI engineer 或 agent engineer，只要不是纯 research，这些八股真的要看。Agent 最终一定跑在一个软件环境、软件系统里，它也要服务化、高可用、存储、网络、监控、部署容灾。传统 SWE 的能力没有消失，只是上面多了一层 AI。作者也感到找工作的压力确实在变大。

## 6. 币安：如何证明 Agent 真的在变好 `27:08 - 30:50`

这一场很多东西作者不太能分享，因为考了很多项目上的细节。它也问了一些比较简单的问题，比如 skill 检索、tool 和 skill 之间的区别，以及 skill 更新怎么做版本化管理。

### 三层问题
1. **架构确认**：你这些是怎么设计的，量级你怎么判断。
2. **路由细节**：你们是不是做了一个路由。很多 skill，每个 skill 能拿到上游投放的某一部分，是让某个 Agent 去选 skill，还是用别的方式。
3. **评估和归因**：你的方案是怎么做 optimize 的；在看 A/B Test 之后，多久可以拿到一个有效的显著性结果；你拿到了这一版方案效果变好，它对 skill 有多大的 impact，你们是怎么 evaluate 的。作者特别提醒：**方案有效和 skill 有效其实是两件事情，中间隔了一层归因问题。**

### 成功会摧毁自己的证据
第三问直接把作者问住了：**你上了新的 skill 之后，原有的 bad case 消失了，然后你的 analyze 就抓不到这里的 bad case，那你怎么知道这个 bad case 是被消灭掉了，而且是因为 skills 里面写的对应内容才被消灭掉的？**

> **仔细品一下**：bad case 消失可能是 skills 起作用了，也可能是流量变了，还可能是上游自己修了。而且它消失以后，监控系统就天然失去了观测它的能力。作者称这是一个**“成功会摧毁自己的证据”**的悖论。

作者当时答得不好，复盘后觉得可以从这些方向回答：
* 保留 hold-out 的流量，不吃新的 skill，用做对照；
* 构造一些回归测试集，定期投放历史的 bad case；
* 在归因上看 skills 的命中日志和 case 消失的时间相关性。

### 五个 trace 怎么合并成一个优化方向
面试官还问了：你拿到了五个调用不同 skill 和工具的有效 trace，怎么把这五个合并成一个对 skill 的优化方向？它的本质是，你优化的东西究竟是一条轨迹，还是一个 skill。

> 面完这些之后，作者最大的感受是：**搭建 Agent 的能力其实不稀缺，稀缺的是证明这个 Agent 在变好的能力。** 全程没有问用什么框架、用什么模型，只关心闭环有没有真的闭上，每一环的因果是不是站得住。

## 7. 复盘出的六层能力 `30:51 - 32:16`

面完这几家公司之后，作者把问题做了一次总结，归纳成六层能力：

| 层级 | 能力维度 | 核心内容与考察点 |
|---|---|---|
| **第 1 层** | **会不会用 LLM** | 包括 prompt、structured output、tool call、基本的模型能力。这是最低的一层。 |
| **第 2 层** | **能不能给 LLM 正确的信息** | 包括 RAG 系统、chunk、embedding、retrieve、top-k，以及 context management。 |
| **第 3 层** | **能不能控制 LLM 的行为** | 包括 workflow、状态机、LLM agent、planning 这些东西。 |
| **第 4 层** | **能不能把 Agent 接到真实世界** | 包括 MCP、外部数据接入、Python 执行之类的能力。 |
| **第 5 层** | **Agent 犯错了怎么办** | 也就是容错、可靠性与兜底机制。 |
| **第 6 层** | **怎么证明 Agent 真的有价值** | 商业价值与闭环验证，作者发现大部分面试官真的非常 care 这一层。 |

在企业里，一个项目是否开展，取决于这个项目的可行性和价值程度。作者觉得这一点大家都应该好好想一想，他自己也在思考目前在做的事情是不是真的有价值。

## 8. 给准备 Agent 岗位的六条经验 `32:17 - 35:20`

1. **不要为了 Agent 而 Agent**：现在搭 Agent 的人很多在做炫技式的堆砌。如果真用了 multi-agent，一定要能回答为什么。一个 pipeline 能解决的，就用 pipeline；一个 SQL 能解决的，就用 SQL；一个 script 能解决的，就用 script。LLM 是系统里面最贵、最慢、最不稳定的组件之一，用它并不是越多越好。
2. **所有技术选型都要准备**：不要只准备“我用了这个”，而要准备为什么是它、为什么不是别的、什么时候你会做一个切换。什么状态结构适合 document store；如果是强一致性数据，你还会不会这么选。
3. **多问自己为什么**：要知其然，并且知其所以然。
4. **传统后端一定不能丢**：作者之前真的没想到 Agent 的岗位可以问这么多后端知识。现在他觉得可以理解，因为 Agent 不是飘在空中的，它最终还是一个 distributed system，后端的东西根本丢不掉。
5. **学会说不确定**：AI 这个领域变得太快，面试官很容易问到你没有实际做过的东西。作者的建议是跟面试官进行交流。没做过的东西硬往自己的项目上加，会有非常多的漏洞和不可行性；不如直接把你对这个项目的看法、以及可以做的 trade-off 讲清楚。现实生产中大家都会用 AI，看的更多是你对 AI 的判断力。可以这样回答：“我没有在生产环境做过，但如果让我设计，我会从几个维度考虑。”这其实考的是一个发散性思维的过程。
6. **学会和 AI 一起工作**：AI Coding 这一轮对作者影响挺大。以前大家把 Copilot 和 Cursor 当工具，但以后很多 software engineer 的工作，可能会变成你负责定义任务、拆任务、做架构、定义约束、验收，让 AI 去生成、搜索、debug。作者觉得 coding interview 也可能慢慢从“你能不能一个人手写所有代码”，变成“当所有人都有 AI 的时候，你能否比别人做出更可靠的系统”。这是一个非常大的变化。

---

## 9. 结论：在不确定的模型外包裹可靠的系统 `35:21 - 36:18`

作者最后的总结是：**AI Agent 工程师本质上正在变成一个 AI-native 的软件工程师。**  
你既不能只懂模型，也不能只懂后端；你既要知道 LLM 有什么能力，也要知道 LLM 有多不可靠，并且能用这些东西把这种不确定性包在一个可靠的软件系统里。这是作者目前对 AI 岗位最强烈的感受。

这篇是作者做的一个完整复盘，其中一些点可能并不十分准确，欢迎大家多多指正。作者也说明这里没有一个标准答案，全部是个人理解。
