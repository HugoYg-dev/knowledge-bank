# 给语言模型装一个动态分类头

做智能体的时候，到处都要做选择。挑工具、给工单分流、判断一段内容是否合规，这些事过去一律交给通用大模型，构造一段提示词，让几十亿参数的自回归模型逐字吐出一段 JSON。慢的时候两秒，快的时候也要几百毫秒，偶尔还会编造工具名，或者 JSON 截断在半路上。

很多人尝试给大模型套上 JSON 约束或结构化输出。这确实管住了格式，输出不会再缺括号，但没解决速度问题。底层依然在自回归循环里转圈，GPU 照样要机械地逐字吐出大括号、字段名、冒号和引号。如果业务要的是高频判定，带着语法约束生成终归也是生成，自回归解码带来的显存带宽开销一点没少，几十毫秒的硬指标依然过不去。

2026 年 9 月 TypeSafe 推出的闭源决策模型 Jev 走红。这个模型完全不生成文字，给它一段状态描述和预设选项，只返回各选项的概率和置信度，延迟七八十毫秒，官方公布的输入单价是每百万 token 0.042 美元，约为前沿大模型的四百分之一。

开源社区的反应极快，短短几周内沿着不同方向跑出了多条平行复现路径。[SemIf](https://github.com/TheoLeeCJ/SemIf-OpenJev) 和塞进浏览器的 [jev-fire](https://github.com/kikoncuo/jevfire) 走最简路线，在完全冻结的预训练模型上直接切词表分值。[train-jev](https://github.com/shibing624/train-jev) 与 [AutoTrust JEV-27B](https://huggingface.co/autotrust/AutoTrust-Decider-Pro-27B) 从原词表复制 24 个固定槽位权重做全分布蒸馏；[Kev](https://github.com/jaredpalmer/kev) 与 [Nimble](https://github.com/bespokelabsai/nimble) 则为了突破固定槽位数量上限，改用序列内指针点积给任意数量的候选项动态打分。还有团队引入跨候选集合注意力来保证选项排列不变性，做出了 [NanoJev](https://github.com/TianyuCodings/NanoJev) 与 [Open-Jev](https://github.com/Zefan-Cai/Open-Jev)，或者干脆换用双向编码器加动态掩码与强化学习校准，端出 4.21 亿参数的 [Laya](https://github.com/NandhaKishorM/laya)。把这些开源实现摆在一起对照，就能看清怎样给语言模型装上一个又快又准的动态分类头。

## 一、直接从因果语言模型词表层切分值

现代因果语言模型的输出层 `lm_head` 本身就是一个大型线性分类器。如果模型的隐藏维度是 1000、词表大小 150,000，最后一层的权重就是 $1000 \times 150000$ 的矩阵。平时生成文本，模型是在这 15 万个候选词里逐个算概率挑下一个词；如果任务只是判断一封工单该转给财务、技术还是销售，候选缩到了 3 个，两边差了五万倍。

**最快的复现方式不需要训练任何新权重。** 提示词送进去跑一次前向传播，取出序列末尾的隐藏状态送入输出层，拿到 150,000 维的分值向量后，直接丢掉其余 149,997 个无关词，只抽出那 3 个候选词对应的分值，在这个小集合内部重新做 Softmax。从概率论看，这一步算的是条件概率，在已知输出必然落在这三个词的前提下，各选项分别占多少。

据[鸭哥 Yage](https://yage.ai/share/jev-timing-analysis-20260919.html) 等社区公开对比评测，开源项目 `SemIf`（[TheoLeeCJ/SemIf-OpenJev](https://github.com/TheoLeeCJ/SemIf-OpenJev)）用完全冻结的 Qwen 4B 跑这套逻辑，零训练零微调，在 Jev 官方 102 个判断任务上达到了 84.5% 的准确率，对比 Jev 自己的 88.3%，差距不到四个百分点。另一个叫 `jev-fire` 的项目则把 0.8B 参数的 Qwen 模型塞进浏览器用 WebGPU 运行，单步决策 71 毫秒，比 Jev 云端 API 的 178 毫秒中位延迟还快，API 费用也直接省掉了。

工程落地上，按照 [Avi Chawla](https://www.dailydoseofds.com/ai-agents-with-langgraph-course-part-1-with-implementation/) 整理的本地复现方案，这套逻辑也不需要自己手动侵入 PyTorch 源码去截取张量。像 SGLang 这样的现代推理引擎已经把 `/v1/score` 打分端点收录为原生接口，客户端传过去提示词和候选词对应的标记编号，服务端在前向传播结束的瞬间直接在显存内完成切片和局部归一化。

```python
import requests

# 工业推理引擎将此抽象为单次打分请求，无需进入解码循环
response = requests.post("http://localhost:30000/v1/score", json={
    "query": prompt,
    "label_token_ids": [token_A, token_B, token_C],
    "apply_softmax": True
})
probabilities = response.json()["scores"]
```

拿到的直接是离散概率分布，整个过程完全跳过了生成循环。几行代码就能跑通这件事，说明从前向传播中提取指定标记的分值并做局部归一化，在算法层面已经相当透明。

跑通单步打分之后，工程落地最容易踩坑的地方出在分词器上。现代语言模型普遍采用字节对编码（BPE，Byte Pair Encoding）分词，**同一个单词前面带不带空格，编码出来的标记编号完全不同**。比如 `billing` 单独出现时编号可能是一万四，前面加个空格就变成两万八。提示词里候选标签紧跟上文，自然带着前缀空格；代码在查找词表索引时一旦漏掉这个空格，拿到的就是另一个语境下的分值，概率分布会严重跑偏。

更棘手的问题出在长单词上。有些词没办法用单个词元覆盖，比如 `technical` 会被分词器切成 `tech` 和 `nical` 两段。取第一段 `tech`，它的分值实际覆盖了所有以 `tech` 开头的单词（`technology`、`technician`、`tech lead`），概率虚高；取最后一段 `nical`，由于前文没有出现 `tech` 前缀，模型在当前位置预测一个孤立 `nical` 的概率接近零，这个选项会被直接误杀。而且长词拆成多个词元后，多步条件概率连乘还会引入长度惩罚偏差。

社区在工程上有两套应对办法。最稳妥也最省事的做法，是在提示词里把选项编成单字母代号，写清楚 A 代表财务、B 代表技术、C 代表销售。在绝大多数主流分词器里，单字母只占一个词元，不会被切碎；模型读完上下文和选项说明后，注意力机制已在末尾吸收了完整语义，单选一个字母几乎没有分词损耗。如果业务非要直接对长短不一的自然语言短语打分，就不能只看末尾单个词元，只能沿着词组逐字算条件概率，把各步对数似然累加起来，再除以带惩罚因子的长度系数 $|W|^\alpha$，抵消长词概率天然偏低的衰减。

## 二、把词表浓缩成 24 槽专用分类头

既然把自然语言选项映射成单字母或数字代号能彻底绕开分词器陷阱，顺着这条路往下走，智能体里五花八门的选择题其实都能收敛为三种标准原语。是非题（`noul`）只判 `false` 或 `true`；无序多选（`choice`）负责工单路由或意图识别，从 `A` 到 `P` 里挑一个字母代号。有序评级（`score`）给故障严重度或内容质量打 `0` 到 `5` 分，除输出各档离散概率外，还能按期望公式 $\mathbb{E}[S] = \sum i \cdot p_i$ 算出 1.84 级这类连续分值，保留程度渐变。

既然所有决策任务只用得上这二十几个固定标记，每次前向传播去算 15 万维的完整词表分值就显得非常浪费。[Xu Ming](https://github.com/shibing624/train-jev) 开源的 `train-jev`（[shibing624/train-jev](https://github.com/shibing624/train-jev/blob/main/README_EN.md)）与 [AutoTrust 团队](https://autotrust.ai/blog/jev-27b-open-decision-model)的 `AutoTrust JEV-27B`（[AutoTrust-Decider-Pro-27B](https://huggingface.co/blog/autotrust/autotrustjev-27b-fast-calibrated-decisions-and-ful)）走的就是这条路，**直接把庞大词表输出层浓缩成一个 24 槽专用分类头**。

这两个项目都以 Qwen 系列模型为主干（如 `Qwen3.5-4B` 和 `Qwen3.8-27B`）。训练时主干网络完全冻结，只挂载一个秩为 16 的 LoRA 适配器和一个 24 槽的 FP32 线性解码头。这 24 个槽位严丝合缝地对应三种决策原语，其中 2 个槽位给是非题（`false` 与 `true`），16 个槽位给多选题（`A` 至 `P`），6 个槽位给评级题（`0` 至 `5`）。输入端把状态描述与多道问题串联成一条序列，每个问题末尾放一个特殊的 `<decide>` 标记；前向传播跑完后，直接抽取 `<decide>` 位置的隐藏状态送进 24 槽分类头，按当前题型切出对应槽位的 logits 做归一化。

这套架构最巧妙的地方在于分类头的初始化与两阶段分布蒸馏。24 槽分类头跳过了随机初始化，在训练开始前直接从预训练主干 `lm_head` 的权重矩阵里，把 `false`、`true`、`0` 到 `5` 以及 `A` 到 `P` 对应的那 24 行权重原封不动地拷贝过来热启动。这样模型还没开始训练，起步输出分布就已经和原始语言模型高度贴近，省去了漫长的冷启动拟合。

在训练流程上，`train-jev` 采用了先蒸馏再精调的两阶段配方。第一阶段做教师全分布蒸馏，拿闭源 TypeSafe Jev v1.13 跑出的 655,806 条样本概率分布当软标签，靠 KL 散度损失拟合完整长尾分布。遇到有序评级（`score`）任务再叠加 0.5 倍排序概率得分（RPS，Ranked Probability Score）损失惩罚跨档越序误差，部分多选题还会随机调换选项位置来压低顺位偏好。第二阶段是金标加规则精调，`train-jev` v0.4.0 混入了 CommonsenseQA、CosmosQA、DynaSent、QSQA 等九个公开数据集与合成规则共约 1.3 万条样本（内含 2,692 条原生软标签），改用交叉熵损失同步更新 LoRA 与分类头，同时把分类头的学习率设为基座学习率的两倍。这套流程跑下来，`train-jev` 在公开评测集上拿到了 76.0% 的准确率和 42.0 的综合决策指数（Decision Index），4B 版本的分类期望校准误差（ECE）控制在 0.062 左右。

`AutoTrust JEV-27B` 则把软标签蒸馏推到了更大规模。它在冻结的 `Qwen3.8-27B` 主干上训练了 1.088 亿参数的 LoRA 加 24 槽分类头（官方报告算力消耗折合约 9.2 亿 B200 GPU 小时），针对 25,376 条持出问题的 Jev 软标签做全分布匹配。训练完的模型甚至不需要在推理期做后验温度调整，在全体决策任务上与原版 Jev 的平均 KL 散度只有 0.017，期望校准误差（ECE）低至 0.0009，几乎复刻了教师模型的置信度曲线。

不过，24 槽固定头也有一道绕不过去的物理边界。问题之间没有自回归交叉依赖，一次前向传播就能并行吐出多题答案，按 `Kev` 基准评测统计，固定槽位批量跑完 5000 道问题只要约 1.8 秒。代价是输出空间在编译期就被锁死在 24 个槽位里。多选题最多容纳 `A` 到 `P` 共 16 个选项，一旦候选列表超过 16 项（比如从上百个工具接口里挑一个），或者运行期需要动态传入训练未定义的新候选集，固定槽位头就无法零代价扩展，超出部分只能拆成多次请求，否则就会落进概率为零的死角。

## 三、用序列内指针头突破候选数量限制

**要让分类头在一次前向传播里对付任意数量的候选项，就必须把分类头的参数维度跟选项个数彻底解耦。** [Jared Palmer](https://github.com/jaredpalmer/kev) 团队开源的 `Kev`（覆盖 `Qwen3.5` 与 `Qwen3.8` 从 [0.8B](https://huggingface.co/jaredpalmer/kev-0.8b)、4B、9B 到 27B 各尺寸）与 [Bespoke Labs](https://github.com/bespokelabsai/nimble) 开源的 `Nimble`（[Bespoke-Nimble-9B](https://huggingface.co/bespokelabs/Bespoke-Nimble-9B)，基于 `Qwen3.5-9B` 挂秩 16 LoRA）换了另一条路。它们用序列内指针点积替代固定槽位，把多选分类改成对序列内各候选项逐一动态打分。

在 `Kev` 的设计里，输入序列严格按照结构化标签拼接，格式为 `<state> ... <q> instructions <opt> 选项1 </opt> <opt> 选项2 </opt> ... <decide>`。背景状态放在最前面，紧接着是问题指令，随后把所有候选选项依次用 `<opt>` 和 `</opt>` 标签包裹起来排成一列，最后以 `<decide>` 标记收尾。模型跑完一次前向传播后，指针头跳过词表和固定槽位，直接抽出每个选项闭合标记 `</opt>` 位置的隐藏状态向量，分别与问题末尾 `<decide>` 标记位置的隐藏状态向量做内积（Dot-Product）。

两个相同维度的隐藏向量求点积，直接产出一个标量分值。如果有 $K$ 个候选项，序列里就有 $K$ 个 `</opt>` 闭合标记，和末尾的 `<decide>` 向量点乘后正好拿到 $K$ 个标量分值，最后送入 Softmax 就能归一化成概率分布（`Nimble` 的做法类似，对每个候选算出标量分值后，是非题过 Sigmoid，多选题过 Softmax）。由于指针头本身只负责特征投影和点积运算，网络参数量与选项个数 $K$ 完全无关。不管传入 3 个选项还是 200 个选项，模型都不需要改动一丁点结构，实测单次查询 200 个候选项的耗时还不到 77 毫秒。参数更新分两档处理。0.8B、4B 和 9B 版本的 `Kev` 冻结主干，只以约 $10^{-4}$ 学习率训练秩 16 LoRA 与随机初始化指针头。到了 27B 规模，`Kev-27B` 先训出权重占比 0.15 的 LoRA，再以 $2 \times 10^{-6}$ 极低学习率把 27B 主干全量微调 1 个轮次（epoch），最后将两部分结果加权融合，进一步压榨大参数主干的判别力。

用因果语言模型挂指针头，最大的隐患来自因果掩码（Causal Mask）的单向视野。因果解码器规定信息只能从左往右单向流动，排在前面的 `<opt> 选项1 </opt>` 根本看不见后面还有哪些竞争选项，排在后面的选项却能把前面的选项看个遍。这种结构上的不对称很容易诱发位置偏见，让模型养成盲目偏爱某个固定顺位（比如总是给第一个或最后一个选项打高分）的坏毛病。更何况，`Kev`（基于 10 个公开语料与合成规则构建约 1.26 万原始样本、约 1 万训练例）和 `Nimble`（仅数千条训练样本）在训练时都没有借用闭源 Jev 的软标签做蒸馏，全程只用硬标签交叉熵（Cross-Entropy）训练，模型更容易顺着位置捷径偷懒。

为了在单向解码器里掰正位置偏见、逼迫指针头紧盯语义证据打分，`Kev` 和 `Nimble` 在数据工程上使出了两套手段。第一套是选项洗牌，`Kev` 在训练过程中对 30% 的样本随机打乱候选项的排列顺序，让同一个正确选项在不同轮次出现在不同位置，打碎位置与标签之间的虚假关联。第二套是对比式数据构造（Contrastive Curation），这也是 `Nimble` 和 `Kev` 的核心数据策略。团队在编写或合成训练样本时，专门成对构造「最小事实翻转样本」，两道题的背景文本和候选项几乎一模一样，只改动背景状态里的一处关键事实，就让正确答案从选项 A 反转成选项 B。模型如果在训练时只记选项表面措辞或排列位置，遇到这种成对样本立刻就会算错拿不到梯度下降，只能被迫去匹配 `<decide>` 与各 `</opt>` 之间起决定作用的证据片段。

## 四、双向编码器、动态掩码与跨候选集合注意力

靠洗牌和对比样本虽然能缓解单向视野的偏见，但因果解码器天生的结构开销依然存在。因果模型在编码长序列时必须维护键值缓存（KV Cache，Key-Value Cache），承担额外的显存与调度成本；而且单向注意力终归不如双向注意力那样能让上下文和所有选项从第一层就对称交互。如果业务需要的是高频调用、每次只要几个浮点数的轻量判断节点，或者要求候选集合在数学结构上严格满足排列不变性（Permutation Invariance），开源社区还探索出了双向编码器动态掩码与跨候选集合注意力两条更彻底的架构路线。

### 双向编码器加动态 `[MASK]`（`Laya`）

[Convai Innovations](https://huggingface.co/convaiinnovations/laya) 开源的 `Laya` 模型放弃了因果解码器，据[魔搭 ModelScope 社区](https://mp.weixin.qq.com/s/9SJf3nhK25rZcZwQNTg7mw)介绍，它在首发版本中直接选用 3.95 亿参数的 `ModernBERT-large` 做主干（算上顶层决策层与行动判断网络，全模型总计约 4.21 亿参数），包含 28 层 Transformer、隐藏维度 1024，采用全双向注意力。同时，按照 `Laya` 论文与代码框架的设计，这套顶层价值策略（VP）决策网络同样支持挂载到 0.8B 至 27B 的任意预训练多模态编码器（支持文本、图像与音频输入）上，并能处理最高 73K 标记的超长上下文。

全双向意味着输入序列里的每一个字、每一个选项描述，在每一层都能互相看见。状态文本和候选选项之间的语义匹配从底层起就是完全对称的，硬件上整个推理变成一次密集矩阵乘法，能把 GPU 的 Tensor Core 打满，4.21 亿参数版本实测单次推理耗时只有 33 到 38 毫秒。

过去用 BERT 做分类，通常是在句首 `[CLS]` 标记后面接一个固定大小的全连接层，类别数同样写死在代码里。为了支持运行期动态传入任意候选项，`Laya` 的做法是在组装输入序列时，给每个选项描述末尾插入一个 `[MASK]` 标记。比如一封退款邮件需要判断转给哪个部门，拼出来的输入就是邮件正文在前，后面依次排列各候选部门的描述，每段描述末尾跟一个 `[MASK]`。这些 `[MASK]` 在全双向注意力下同时聚合邮件正文和各自部门说明，并在同一层里兼顾其他选项。不管传入 2 个选项还是 20 个，只要在输入里增减 `[MASK]` 数量，网络结构一点不用改。

因为文本长短不一，每个 `[MASK]` 在序列中的物理位置动态变化，短邮件的 `[MASK]` 可能在第 15 位，长邮件可能跑到第 300 位。程序在分词阶段记下各 `[MASK]` 索引位置，随后调用 PyTorch `torch.gather` 算子，直接按索引从几百行大矩阵里抽出目标行，拼成规整的候选张量。这步只做显存地址重排，耗时在微秒量级。抽出来的向量映射为标量分值后，考虑到 2 个选项瞎蒙概率是 50%、20 个选项只有 5%，`Laya` 还针对任务类型和选项数量预先拟合了动态缩放参数，在 Softmax 前对分值做调节，保证不同候选数量下的概率具有一致的统计尺度。

### 跨候选集合注意力与排列不变性（`NanoJev` 与 `Laya` 决策层）

把各个候选项的特征向量抽出来之后，如果只是把每个向量单独送进共享的线性层或 MLP 算一个分值，各个选项在进入最后的 Softmax 之前其实是「盲审」状态，彼此不知道对手拿了多少分、长什么样。**要让候选项在打分前同台比对，必须在候选特征之上再加一层跨候选交互网络。**

`Laya` 的做法是在 ModernBERT 主干编码完成后，额外叠加两层 Transformer 决策层，然后再去抽取 `[MASK]` 向量。整条序列经过这两层顶层交互后，各个 `[MASK]` 位置既能继续参考共享的上下文语义，又能让不同选项向量之间互相计算注意力，拉开彼此的区分度并建立竞争关系。

[Tianyu](https://huggingface.co/C-Tianyu/NanoJev) 等人开源的 `NanoJev`（`TianyuCodings/NanoJev`，基于 `Qwen-0.6B` 主干）以及 [Zefan-Cai](https://zefan-cai.github.io/open-jev/) 开源的 `Open-Jev`（`Zefan-Cai/Open-Jev`）则把跨候选交互提炼成了专门的集合注意力层（Set-Attention）。`NanoJev` 最初面向迷宫、贪吃蛇、基础射击和移动射击等实时交互游戏决策设计，输入包含当前环境状态、问题以及 2 到 255 条候选路径。模型以 $10^{-5}$ 的较低学习率微调 0.6B 主干与共享评分头，在四类游戏按 1/3 迷宫、1/3 贪吃蛇、1/6 基础射击、1/6 移动射击混合的约 18,760 道专家演示题上训练。

在处理多选题（`Choice`）时，`NanoJev` 先将状态与每条候选路径编码成特征向量，随后把整组候选特征送入一个无位置编码的集合注意力模块（Set-Attention Layer）做全局聚合，最后对整个选项集合一起计算分类交叉熵损失（是非题则用 Sigmoid 预测真值概率，评分题输出概率加权的期望等级）。因为集合注意力层内部去掉了相对位置偏置，对输入候选项集合做的是完全对称的全局自注意力交互，所以它在数学上严格满足排列不变性。不管你在推理时把候选列表的顺序怎么随机打乱，集合注意力层算出来的各选项概率分布都分毫不差。得益于这套轻量集合交互结构，`NanoJev` 不需要重新训练就能在单次前向中稳定处理多达 255 个候选项，综合任务成功率大幅甩开未调优的原始 Qwen 模型，逼近闭源 Jev。

## 五、系统该不该自己拿主意

不管底层用的是词表切片、24 槽头、指针点积头还是集合注意力头，只要最后一步是把分值送进局部 Softmax，工程落地就必须面对两个生死攸关的问题。一是遇到训练范围之外的异常输入（Open-Set）怎么拒答，二是拿到概率数字后怎么决定该由系统自动执行还是转交人工。

局部 Softmax 算的是闭集条件概率，建立在「真实答案必然落在给定候选项内」这个强假设上。一旦系统碰上黑客注入邮件、缺失关键上下文的残缺工单或完全无关的异常输入，由于 Softmax 分母被锁死在给定选项内，错误选项照样会强行瓜分全部概率。哪怕在正常业务范围内，单靠最高概率（Top-1 Probability）设一个固定阈值也很容易翻车。比如面对两个选项给出 51% 和 49% 的概率，最高分勉强过半，但两个选项咬得死紧，误判风险极高；而十个选项里第一名拿到 60%、其余九个都在 4% 上下时，虽然绝对值只有六成，它却高出第二名五十多个百分点，模型其实非常笃定。

围绕开放集拒答与自主行动门控，开源社区演化出了三道层层递进的工程防线。

### 第一道防线，显式保留退路选项

最直接的做法是在候选列表里永远保留一个兜底标记，比如 `OTHER`、`NO_MATCH` 或「转人工」，给预设范围之外的输入留出安全出口。不过这种做法对固定槽位模型很不友好。像 24 槽固定头本身就没有专门为开放域拒答设计独立的动态分布机制，强行把超出范围的输入映射到某个冷门槽位，输出的概率往往接近零或者随机乱跳。

### 第二道防线，缺失信息样本的均匀分布训练与温度校准（`Kev` 与 `Nimble` 路线）

为了让指针头学会在证据不足时主动踩刹车，`Kev` 在构造那 1 万多条训练样本时，专门针对已有决策问题合成了一批删掉关键证据的「无需答案」变体。遇到这类无法做出确切判断的样本，训练目标直接要求模型对所有候选项输出完全平坦的均匀概率分布（或者激活专门的 `p_none` 拒答损失），相当于教模型在看不懂或证据缺失时把归一化香农熵拉到最高，主动承认「所有选项都不匹配」。

在此基础上，`Kev` 和 `Nimble` 都会在独立的保留验证集上拟合温度系数 $T$，对输出的 logits 做事后温度缩放（比如 `Nimble` 发布的 LoRA 检查点默认校准温度约为 2.179）。温度校准的提振效果非常直观。在 `Kev` 保留评测集 `decision-v7` 与跨任务泛化集 `transfer-v4/v9` 上，温度缩放把 `Kev-9B` 的期望校准误差（ECE）从 0.103 直接压到 0.041，同时维持准确率不变。更要紧的是，置信度在 0.9 以上却答错的高危盲目错误率，从校准前的 8.2% 降到了 2.4%。按最大 5% 错误率预算（Coverage at 5% Error）卡线，校准后的 `Kev-9B` 能自动接管 45% 到 57% 的线上决策流量（闭源原版 Jev 在同一指标下约为 70%），其余疑难请求则稳稳拦下，转交人工或大模型处理。

### 第三道防线，1028 维独立行动判断网络与 62.5% 损益底线（`Laya` 路线）

为了彻底区分「两选项 51% 对 49%」和「十选项 60% 领跑」这两种截然不同的分布局面，`Laya` 放弃了单一概率阈值，单独搭了一个行动判断网络（Act Head）。它接收一个 1028 维拼接向量。前 1024 维取自整篇上下文池化后的 `[CLS]` 全局语义表征；后 4 维刻画当前概率分布形状，依次为最高概率（Max Probability）、前两名概率差值（Top-2 Margin）、归一化香农熵（Normalized Entropy），以及当前选项数占系统上限 255 的比例（$K / 255$）。全局语义向量负责感知输入文本本身是否复杂、残缺或存在越狱异常，四维统计量负责读懂概率分布的陡峭程度；两部分拼在一起送进两层全连接网络，直接输出「自动执行」和「升级给人工（Abstain）」两个动作的概率。前面提到的闭集异常输入，也正是在这一步被全局语义表征和归一化熵联手兜住。

行动网络的放行门槛直接由 `Laya` 的成本敏感奖励矩阵算出。**在训练规则里，自动执行且结果正确记 +1.0 分，自动执行却做错重罚 -3.0 分，拿不准升级给人工的固定成本是 -0.5 分。** 设模型对当前第一名选项的真实把握为 $p$，自动执行的期望收益就是 $p \cdot 1 + (1 - p) \cdot (-3)$，化简后是 $4p - 3$；只有当 $4p - 3 > -0.5$、即解出 $p > 0.625$（62.5%）时，自动执行才比转人工划算。受这套损益矩阵考核，模型内部会自然学出一条安全底线，把握不到六成出头时老老实实交出控制权。

### 概率值得信赖的训练根基

无论是 `Kev` 按 5% 错误率预算切流量，还是 `Laya` 按 62.5% 损益线放行，整套门控能够成立的前提，是模型吐出来的概率数字真的代表客观正确率。

传统硬标签交叉熵分类只有当正确选项分值趋近无穷大时损失才最小，模型天然被推向过度自信。`Kev`、`Nimble` 和 `NanoJev` 全程只用硬标签交叉熵训练，即便事后靠温度缩放把第一名置信度拉准，也只能保证榜首概率具备校准意义。排在第二、第三位的长尾候选从未受过真实分布形态约束，分值高低缺乏严格统计含义。如果业务需要连同次选方案、第三候选方案的长尾概率一起拿来做组合路由（比如次选部门概率超 25% 就并行抄送），训练阶段就必须换用软分布匹配或严格适当评分规则。

这就是为什么 `train-jev` 和 `AutoTrust JEV-27B` 坚持用几十万条软标签跑 KL 散度加 RPS 蒸馏，借教师模型的软分布把长尾候选的相对赔率一并学过来；而 `Laya` 则走得更远，采用校准决策强化学习（RLCD，Reinforcement Learning for Calibrated Decisions），把奖励函数换成决策理论里的严格适当评分规则（Strictly Proper Scoring Rules）。在数学上，一个评分规则被称为严格适当，当且仅当模型报告的概率分布恰好等于客观真实分布时，期望奖励才唯一达到最大值。`Laya` 在训练中组合了对数评分（重罚对正确类别给低概率的情况）、球面评分（提供有界平滑梯度防止策略梯度爆炸）和排序概率评分（教模型理解有序档位远近），在训练期直接逼着模型如实交代每项候选的真实把握。

据[郝博阳](https://mp.weixin.qq.com/s/E1fvA95qGkEnKinTAACWaA)《[一文拆解 Jev 架构](https://mp.weixin.qq.com/s/E1fvA95qGkEnKinTAACWaA)》整理的独立研究者 Archer Hume 黑盒测谎实验，经过这类校准训练的 Jev 模型在 1200 道 MMLU 标准化测试题上测得的期望校准误差只有 0.031。在 30 道简单乘法题上，Jev 答对了 86.7%，自报平均把握是 83%，两者高度贴近；当题目换成难度更高的两步算术应用题，正确率跌到 32%，模型也同时把自报把握降到了 30%。置信度随题目难度同步下调，正是校准训练赋予决策模型的核心资产。至于严格适当评分损失推导、两级温度标定与置信度级联成本账单，可进一步参考姊妹篇《决策模型的概率校准、置信度级联与端侧平替账单》。

## 六、打包多维度问题并发与两种生产部署形态

在真实业务里，一封客户邮件或一条用户请求进来，往往需要同时回答好几个维度的问题，比如分流到哪个部门、紧急程度几级、有没有流失倾向、里面是否夹带钓鱼或越狱内容。如果依靠通用生成大模型，要么串行调四次累计耗时数秒，要么把四个问题硬塞进一段很长的提示词里指望一次性吐出复合 JSON，极易漏字段或破坏格式。

换成动态分类模型后，多问题并发在工程上有两套高效的注意力隔离方案。像 `Laya` 这类几亿参数的双向编码器，既能把同一封邮件正文与不同问题拼成批处理一次送进显卡，也能在单条序列里串联多道题并挂上动态注意力掩码，将非本题区域的注意力权重强制置零，使每道题的 `[MASK]` 只看见共享正文和自身候选项。换成 `train-jev`、`AutoTrust JEV-27B` 或 `Kev` 这类 Qwen 因果解码器模型，则可以把所有问题接在共享状态 `<state>` 后面，靠块状注意力掩码向所有问题开放 `<state>` 读取权限（或在编码完共享正文后冻结键值缓存分出多条平行分支），同时屏蔽不同问题之间的横向注意力，一次前向传播就读出全部 `<decide>` 位置的判定结果。

《一文拆解 Jev 架构》引述过 Archer Hume 的暗号隔离实验。他在问题 A 题干里塞入暗号 `ZEBRA-7741`，再让相邻的问题 B 从选项里猜这串暗号，Jev 选中正确答案的概率严格为 0；可只要把同一句暗号挪进所有问题共享的状态文本 `<state>`，问题 B 的正确率立刻跳到 90% 以上。共享上下文对所有题目开放，相邻题目之间则严格物理隔离，彻底杜绝了多维判定时的前后串台。

当这套多问题并发的动态分类模型落地到生产集群时，根据团队手头的显卡资源与业务架构，通常会采取两种截然不同的部署形态。

### 第一种形态，独立轻量小模型前置当流量网关

**轻量分类头与重型生成模型在生产集群里可以既分立又合一。** 如果线上主力生成服务调的是昂贵云端商业 API，或者本地跑着百亿、千亿参数的重型模型，最划算的做法是在最前面单独放一个几亿参数的轻量决策模型当反射网关。比如 4.21 亿参数的 `Laya`、6 亿参数的 `NanoJev` 或 8 亿参数的 `Kev-0.8B`，显存占用不过几百兆到一两吉字节，甚至能用 ONNX Runtime 或 WebGPU 跑在边缘节点上。工单分流、工具参数合规检查、意图识别和安全拦截在三十到七十毫秒内就能全部过一遍，把八成以上的常规判定挡在第一线；包括「当前请求该不该调用重型推理模型」这道模型路由题本身也是一次分类，完全可以交给前置小模型单步拍板。重型生成大模型退居二线，只在需要写长文本、解释复杂逻辑或做多跳推理时才接手。

### 第二种形态，同主干「专家块」双系统复用（Blocks of Experts）

如果业务团队本来就在本地显卡上部署了中等或较大规模的开源生成模型（比如在一张 40 GB 显卡上跑 `Qwen3.5-9B`，或者在一张 80 GB 显卡上跑 `Qwen3.8-27B`），再额外维护一套异构的 ModernBERT 或小尺寸 Qwen 反而会增加模型加载与运维调度的复杂度。针对这种场景，`AutoTrust JEV-27B` 给出了「专家块（Blocks of Experts）」同主干双系统部署方案。

在这套架构下，显存里只驻留一份冻结的 `Qwen3.8-27B` 预训练主干权重，同时承担慢思考生成（系统 2）与快思考判定（系统 1）两套职责。收到常规对话或长文生成请求时，推理引擎（如 vLLM）直接走原始 `Qwen3.8-27B` 主干与原生 `lm_head` 自回归解码；一旦收到结构化分类、评分或安全审查请求，vLLM 路由在同一个 27B 主干上动态激活 1.088 亿参数的系统 1 专家块（即秩 16 LoRA 适配器加 24 槽分类头，或像 `Kev`、`Nimble` 那样动态挂载几千万参数的 LoRA 加指针头），单次前向传播直接吐出校准概率。一份主干显存开销，同时拥有百亿级模型的深层语义理解力与单步分类头的毫秒级确定性输出。

无论选用独立小网关还是同主干双系统，把动态分类头接进生产流水线前都得先算清经济账。它最管用的位置，是那些标准明确、证据集中、判错了容易复核或重跑的节点。假如后续生成大模型本来就得无条件跑一遍，并且能在生成回复时顺手做完筛选，强行在前面串一层独立分类拦截器，一旦误判触发来回重试或串行等待，整条调用链的端到端延迟反而会翻倍。

## 七、拼成代码

下面把前面拆解的三种核心动态分类头架构，分别是 24 槽词表热启动固定头（`train-jev` 与 `AutoTrust JEV-27B` 路线）、序列内指针点积打分头（`Kev` 路线），以及带跨候选交互与 1028 维行动判断网络的动态掩码分类头（`Laya` 与 `NanoJev` 路线），写成可直接对照的 PyTorch 模块。

```python
import math
import torch
import torch.nn as nn
import torch.nn.functional as F


class Slot24VerbalizerHead(nn.Module):
    """
    24 槽固定分类头 (train-jev / AutoTrust JEV-27B 路线)
    2 槽 noul (false/true) + 16 槽 choice (A~P) + 6 槽 score (0~5)
    支持从预训练语言模型 lm_head 对应 token 行直接拷贝权重热启动。
    """
    def __init__(self, hidden_dim, pretrained_lm_head_weight=None, slot_token_ids=None):
        super().__init__()
        self.proj = nn.Linear(hidden_dim, 24, bias=False, dtype=torch.float32)
        if pretrained_lm_head_weight is not None and slot_token_ids is not None:
            if len(slot_token_ids) != 24:
                raise ValueError("slot_token_ids 必须恰好包含 24 个词表索引")
            with torch.no_grad():
                selected = pretrained_lm_head_weight[slot_token_ids].to(torch.float32)
                self.proj.weight.copy_(selected)

    def forward(self, hidden_states, decide_indices, task_type="choice", num_choices=4, temperature=1.0):
        if temperature <= 0:
            raise ValueError("temperature 必须大于 0")
        # 抽取每个问题末尾 <decide> 标记位置的隐藏状态: [batch_size, hidden_dim]
        batch_indices = torch.arange(hidden_states.size(0), device=hidden_states.device)
        decide_reps = hidden_states[batch_indices, decide_indices].to(torch.float32)
        all_logits = self.proj(decide_reps) / temperature

        if task_type == "noul":
            logits = all_logits[:, 0:2]
            return F.softmax(logits, dim=-1)
        elif task_type == "choice":
            if not (1 <= num_choices <= 16):
                raise ValueError("固定 24 槽分类头的 choice 任务仅支持 1 到 16 个候选项")
            logits = all_logits[:, 2:2 + num_choices]
            return F.softmax(logits, dim=-1)
        elif task_type == "score":
            logits = all_logits[:, 18:24]
            probs = F.softmax(logits, dim=-1)
            levels = torch.arange(6, device=probs.device, dtype=torch.float32)
            expected_score = torch.sum(probs * levels, dim=-1, keepdim=True)
            return probs, expected_score
        else:
            raise ValueError("未知的 task_type")


class PointerScoringHead(nn.Module):
    """
    序列内指针点积打分头 (Kev 路线)
    抽出每个选项末尾 </opt> 的隐藏状态与问题末尾 <decide> 的隐藏状态求缩放点积，
    支持任意数量的动态候选项。
    """
    def __init__(self, hidden_dim):
        super().__init__()
        self.query_proj = nn.Linear(hidden_dim, hidden_dim, bias=False)
        self.option_proj = nn.Linear(hidden_dim, hidden_dim, bias=False)
        self.scale = 1.0 / math.sqrt(hidden_dim)

    def forward(self, hidden_states, decide_indices, opt_end_indices, opt_padding_mask=None, temperature=1.0):
        if temperature <= 0:
            raise ValueError("temperature 必须大于 0")
        batch_size, _, dim = hidden_states.shape
        if opt_end_indices.size(1) == 0:
            raise ValueError("opt_end_indices 至少需要包含一个候选项")
        hidden_states = hidden_states.to(self.query_proj.weight.dtype)
        batch_idx = torch.arange(batch_size, device=hidden_states.device)

        # 抽取 <decide> 向量: [batch_size, 1, dim]
        q_rep = self.query_proj(hidden_states[batch_idx, decide_indices]).unsqueeze(1)

        # 用 gather 抽取动态数量 </opt> 位置的隐藏向量: [batch_size, num_options, dim]
        idx = opt_end_indices.long().unsqueeze(-1).expand(-1, -1, dim)
        opt_reps = self.option_proj(torch.gather(hidden_states, dim=1, index=idx))

        # 点积求每个候选项的标量得分: [batch_size, num_options]
        scores = (torch.bmm(opt_reps, q_rep.transpose(1, 2)).squeeze(-1) * self.scale).to(torch.float32)
        if opt_padding_mask is not None:
            if torch.any(torch.all(opt_padding_mask, dim=-1)):
                raise ValueError("每个样本至少需要保留一个未被遮蔽的有效候选项")
            scores = scores.masked_fill(opt_padding_mask, float("-inf"))

        probs = F.softmax(scores / temperature, dim=-1)
        return probs


class DynamicClassificationHead(nn.Module):
    """
    双向动态掩码与跨候选交互分类头 + 1028 维行动判断网络 (Laya / NanoJev 路线)
    假定当前 batch 内各样本的候选项数量一致为 K (mask_indices 维度为 [batch_size, K])。
    """
    def __init__(self, hidden_dim=1024, num_decision_layers=2, max_options=255):
        super().__init__()
        if max_options <= 0:
            raise ValueError("max_options 必须大于 0")
        self.hidden_dim = hidden_dim
        self.max_options = max_options

        # 顶层决策层，在全序列或候选集上交互并强化各选项的区分度
        encoder_layer = nn.TransformerEncoderLayer(
            d_model=hidden_dim,
            nhead=8,
            dim_feedforward=hidden_dim * 2,
            activation="gelu",
            batch_first=True,
        )
        self.decision_layers = nn.TransformerEncoder(
            encoder_layer,
            num_layers=num_decision_layers,
        )

        # 选项评分器，把每个候选掩码向量映射为一个标量分值
        self.option_scorer = nn.Sequential(
            nn.Linear(hidden_dim, hidden_dim // 2),
            nn.GELU(),
            nn.Linear(hidden_dim // 2, 1),
        )

        # 行动判断头，接收 1024 维全局语义与 4 维分布统计量 (共 1028 维)
        self.act_head = nn.Sequential(
            nn.Linear(hidden_dim + 4, 128),
            nn.GELU(),
            nn.Linear(128, 2),
        )

    def forward(
        self,
        hidden_states,
        mask_indices,
        cls_vector=None,
        key_padding_mask=None,
        temperature=1.0,
    ):
        if temperature <= 0:
            raise ValueError("temperature 必须大于 0")
        batch_size, seq_len, dim = hidden_states.shape
        num_options = mask_indices.shape[1]
        if num_options == 0:
            raise ValueError("mask_indices 至少需要包含一个选项")

        # 经过顶层决策层交互后再抽取选项表征
        enhanced = self.decision_layers(
            hidden_states,
            src_key_padding_mask=key_padding_mask,
        )

        # 用 gather 抽取各选项 [MASK] 位置的隐藏向量
        idx = mask_indices.long().unsqueeze(-1).expand(-1, -1, dim)
        option_reps = torch.gather(enhanced, dim=1, index=idx)

        # 映射为 FP32 标量分值并按温度缩放，确保半精度输入下熵计算数值稳定
        logits = self.option_scorer(option_reps).squeeze(-1).to(torch.float32)
        probs = F.softmax(logits / temperature, dim=-1)

        # 提取四维分布统计量: 最高概率、前两名差值、归一化熵、选项容量占比
        max_p, _ = torch.max(probs, dim=-1, keepdim=True)
        top2, _ = torch.topk(probs, k=min(2, num_options), dim=-1)
        if num_options >= 2:
            margin = (top2[:, 0] - top2[:, 1]).unsqueeze(-1)
        else:
            margin = torch.ones_like(max_p)

        eps = 1e-9
        entropy = -torch.sum(probs * torch.log(probs + eps), dim=-1, keepdim=True)
        norm_entropy = entropy / math.log(max(num_options, 2))
        budget_ratio = torch.full_like(max_p, num_options / float(self.max_options))

        stats = torch.cat([max_p, margin, norm_entropy, budget_ratio], dim=-1).to(enhanced.dtype)

        # 拼接语义向量与四维统计量，判断自动执行还是转交人工
        if cls_vector is None:
            cls_vector = enhanced[:, 0, :]
        action_logits = self.act_head(torch.cat([cls_vector, stats], dim=-1))

        return probs, action_logits
```
