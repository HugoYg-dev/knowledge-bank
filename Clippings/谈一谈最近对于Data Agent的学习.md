## 从 0 搭一个 Data Agent，要做哪些取舍？

这几个礼拜我一直在看 Data Agent 的落地文章。看的几个案例的业务场景差得挺远，有做企业语义层的，有做连锁零售经营问数的，有做电商 GMV 分析的，还有一个是通用的数据助理框架，但读下来它们其实都围绕一类问题，自然语言让提问这件事变容易了，要让Data Agent 做得更好，挺不容易。

---

## 一、1.0 版本要选定好方向

有的做法在 1.0 版本里只做经营分析的高频场景，销量、客户、区域、预算、同比，支持单轮问答和多轮追问，权限直接复用 BI 的行级权限，财务结算、供应链明细、自定义权限、多图联动大屏一概不做。它还主动放弃了直接让模型写 SQL 这条路，改成让模型去调用 BI 已经定义好的指标和查询能力，口径交给 BI 语义层，权限由查询引擎强制执行，性能复用 BI 已有的预聚合和缓存。

仔细一想，确实如此，我以前觉得 Data Agent 的能力当然是越多越好，覆盖面越广越有价值，第一版就该往大了做。看完才发现，把系统不做什么写清楚，和把要做什么写清楚一样重要。范围放开之后，出了问题很可能会说不清楚是哪一块没做好，也没法判断这一版到底ok不ok。、我以前会总想第一版就做把范围定广，这样后续一点点迭代优化就好，可惜把“当前版本暂时做不了”只当成系统的能力不足，如今看它更像是 1.0 必要的一部分。

---

## 二、语义层是资产，还是一次性的提示词

口径这件事我一直觉得比较麻烦，“销售额”是含税还是不含税，退单算不算，跨月订单算在哪个月，“大客户”是按签约金额还是按回款，业务自己内部就有好几种说法。现在要把这些说法固定下来，交给一个系统去执行。 一种做法是把业务知识整理成标准资料 ，分成术语、业务对象及关系、指标、任务剧本四类，每份资料都有负责人、版本、权限和审批。 用 Git 保存每一次修改，再配一套分级 CI 自动检查 ，从 Schema 合法性、引用一致性一直查到指标安全、权限兼容、行为回归和检索回归。

> 不太明白？没关系，换个说法。这几类资料都放在一个代码仓库里，和写代码一样。有人要改“销售额”的口径，先改文件、提交一次修改，再交给人审核。审核之前系统会自动跑一遍检查：指标定义有没有写错，引用的字段和数据表还在不在，权限有没有冲突，以前能答对的问题改完还对不对。全都过了才允许合并。上线以后发现不对，直接回滚到上一版就行。

语义层在几种做法里的形态不一样。有的把知识拆成术语映射、指标口径、数据资产字典、分析方法、拒答话术和示例问答六块，按需检索注入，单轮注入控制在 3500 token 以内。有的用一个语义层加指标注册表加血缘图谱。还有的把本体做成五份结构化文件，业务对象、指标口径、对象关系、黑话词典和全局配置，当成翻译和校验的唯一事实源，JOIN 键、必要过滤。

形态可以选，共同点是口径、字段、JOIN、过滤和权限不能让模型每次现写现猜。做法是把“业务上什么叫对”登记下来，让它可检索、可校验、可版本化。里面有一点我很认同，语义层要有版本、有 Owner、有评审、有回滚，运行时还要固定语义版本，这样每一句回答都能说清用了哪一版定义、哪张表、哪条权限，出问题能回溯到具体哪一版的哪个改动。

还有一个容易被忽略的地方是冷启动。语义层没法一次建完，总会有指标还没注册。这时候可以允许在隔离的探索链路里先查一次，结果稳定、业务也认可它有长期价值，就从这次查询里反推出指标公式、分析维度和必要过滤条件，人工确认之后再注册进正式语义层。这条探索链路是必要的，但探索出来的东西不能自己变成正式口径，若非如此第一版能回答的问题会少得没法用。

---

## 三、模型该不该直接写 SQL

我发现，现在优秀的实操项目没有一个是让模型从自然语言直接跳到 SQL。

有的走 NL2BI，模型不自己编口径（写SQL），去调用 BI 已经定好的指标。有的在中间加一层业务语义模型，自然语言先生成受约束的业务表达，再由确定性引擎翻译成 SQL。还有的做得更严，模型只能写业务语义稿，稿子里出现物理表名或字段名就直接判错，表怎么选、JOIN 怎么写、过滤怎么加，全交给翻译引擎。还有一种做法是把意图、语义上下文、语义计划、执行计划、证据包都做成强类型中间态，模型的理解和最终执行被拆开，中间每一步都能检查和回放。

直接写 SQL 的问题不只是语法可能出错。更麻烦的是模型要在一次生成里同时猜业务含义、表、字段、JOIN 方式、过滤条件和聚合方式，六件事压在一次输出里，猜错的概率层层叠加，错了之后还没法说清是哪一层错。中间表达把这几件事拆开了，模型只管把自然语言变成受约束的业务表达，物理表名、JOIN 方式这些留给后面的确定性模块。

---

## 四、工具要少，而且职责要正交

有的方案一共七个工具，真正的取数入口只有一个，其余分别负责主题列表、表结构、指标口径、权限预检、图表渲染和报告生成。另一个方案是通过多个工具访问后端引擎，所有引擎能力只从这一个出口走。工具之间的职责重叠越多，模型选错的概率越高，出了问题也越难定位是哪一次调用带偏的；出口越集中，权限审计、异常处理和回归测试越好做。

错误也要有结构。有的查询工具会返回具体的异常码，累计字段误用 SUM、结果行数过大、权限不足、字段不存在、查询超时各算一类，模型按错误码决定是收紧条件、重新检索、拒答，还是转成异步报告。只返回一句“查询失败”，显然是无法继续往下排查的。

---

## 五、规则该写进提示词，还是写进引擎

这是我觉得最容易被低估的一个岔路。

有的做法是在提示词里写铁律，比如累计数据不能随便相加、同比必须用相同月份范围、没有权限不能返回数据，这类规则写得清清楚楚。但同样的规则在查询引擎里又硬校验了一遍，这样模型漏了系统可以作为兜底。还有的做法用短时令牌来卡流程，确认、查询、探索三类操作各有一枚，令牌绑在语义稿或 SQL 的指纹上，内容被替换就失效。执行器再做一次只读拦截和行数上限，生成的 SQL 要先过一个校验环节才能执行，需要跑 Python 的时候放到沙箱里。

> 就拿“查今年累计销售额”来说。提示词里会告诉模型累计数据不能直接相加，但模型可能会忘（还有可能上下文太大，这部分模型没有“注意”），所以查询引擎收到 SQL 以后，自己再检查一遍有没有对累计字段用 SUM。引擎才是最硬的那道关，模型记不记得都拦得住。
> 
> 令牌是另一层，用来防住流程被绕过。用户确认了口径，系统发一张和这次查询绑定的令牌，引擎执行时核对令牌和内容对不对得上，对不上就拒绝执行，免得有人跳过翻译引擎直接查库。执行器那边还定了只读和返回行数的上限，生成的 SQL 执行前要先过一遍校验，要跑 Python 分析就放到沙箱里。

所看的博客中，对于规则的态度是一致的。提示词能约束模型的倾向，真正需要兜住的规则得放到查询引擎、翻译器或执行器里做硬校验。

## 六、拒答算不算失败

一句话，拒答不算失败。 有的把拒答列成合法终态，有的专门维护拒答话术库 ，把“为什么答不了”写成标准话术，还有的把探索链路和正式取数链路物理隔开。域外的问题、越权的数据、缺失的字段、过大的结果、超时的查询、冲突的口径，每一样都要有固定的结果。

能说清楚为什么现在不能答、下一步该做什么，比硬凑数字更像一个生产服务。我见过一些 demo，宁可返回一个看起来合理的数字也不说不知道，那种系统没法进生产。用户拿着一个错数字做了决策，代价比拿不到数字大得多。

## 七、知识从哪来，谁能发布

知识怎么来、怎么更新，这几篇都当成工程问题在处理，没有一个是靠前期一次性导入文档解决的。

术语从真实的提问日志里补，用户怎么叫这个指标就记下来。规则来自线上出问题的地方，先把真实翻车记录下来，再把根因固化成一条规则。血缘从 ETL 和元数据里自动解析。指标通过注册表或本体维护，走变更流程。

发布权单独说一句。有的做法是让评测结果、实体体检和线上 badcase 汇成一个统一的建议池，一次反馈对应一个根因和一个修改请求，模型只能提建议，合并和发布由人来做。

我原来以为知识治理是把文档写全写细，后来理解变了，知识是采集、审核、发布、复用、反馈这样一个循环，谁来审核、怎么回滚，比文档写得全不全更要紧。

## 八、评测只测答案，还是测整条链路

评测只盯最后那句话像不像，很多问题测不出来。有的方案建了五层验证，从单点验证、口径一致性、黄金集，一直到安全压测和性能压测。有的用六个维度的评分，看的不只是最终文本，还包括工具调用的顺序、生成的 SQL、诊断树和事实的一致性。通用框架那篇准备了 29 条真实需求做金标准回归，另外配了 171 项单测和 CI 门禁。

这些评测合起来在回答同一个问题，这次出错到底是哪一层出的。是模型没听懂，还是语义层没有这个定义，还是权限给错了，还是工具选错了。没有这个归因，出了问题只能凭感觉调提示词，调完也不知道有没有真修好。评测之外还有灰度，先内部团队用，再放一小批业务用户，最后才扩大，上线以后继续从真实提问里补术语，从真实翻车里补规则。规则改了要重新跑回归。

## 最后剩下的那点判断

这几个岔路看下来，选哪条不是能力高低的问题，是团队愿意长期维护哪一块的问题。同一个功能，放在提示词里、放在语义层里、放在引擎里，做法差很多，维护成本也差很多，但放在哪里都要能定位到是哪一层出的错。

Data Agent 的落地顺序，我现在觉得比模型选型更清楚。先把业务上什么叫对写进语义资产，再把什么情况下允许执行写进确定性引擎，最后才是让模型在这套边界里把理解、路由和组织回答做得更好。模型是可以换的，语义资产、执行契约和评测门禁才是要一直优化着的东西。
